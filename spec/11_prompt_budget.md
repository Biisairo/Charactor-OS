## 1. 개요

### 1.1 목적

프롬프트 예산이 **틀린 자로 재고 있었다.** 그 결과 소민찌는 뇌가 도구로
모아온 근거를 하나도 발화 프롬프트에 싣지 못했고, 그 사실이 어디에도
드러나지 않았다.

세 가지를 고친다 — 자를 정확히 재고, 예산을 모델에 맞게 정하고, 예산이
모자란 사실을 드러낸다.

이 문서는 구현 착수 전 단일 진실 공급원이다. 코드와 충돌하면 이 문서가 이긴다.
TASK-24의 상세 명세이며, `docs/TASKS.md` 3.24는 발견 경위만 남긴다.

### 1.2 현재 상태(문제 정의)

측정된 사실이다. 추정이 아니다. 근거는 `logs/llm_calls.jsonl`(2,036 호출)이다.

| # | 사실 | 근거 |
|---|---|---|

| P-3 | 실제 고정 섹션은 **2,141 토큰**(예산의 71%)이다. 859 토큰이 남아 있었는데 추정 오차 때문에 버렸다 | 보정 계수 기준 재계산 |

요약: 계측이 틀려 예산이 없다고 판단했고, 없다고 판단한 사실조차 보이지 않았다.

### 1.3 범위

**포함**

- 실제 토크나이저 기반 토큰 계측과, 그것을 쓸 수 없을 때의 폴백
- 어느 계측기가 쓰이고 있는지의 관측 가능성
- 프롬프트 예산과 토크나이저의 모델별 설정화
- 고정 섹션별 상한과 초과 보고
- 예산 부족·절단 사실의 운영 로그·트레이스 노출
- `transformers` 의존성 선언

**제외 (비목표)**

- 고정 섹션의 **절단**. 자르지 않는다 — 예산이 모자라면 알리고, 자산을 고치는
  것은 사람의 몫이다 (결정 5). 상한을 두는 것과 자르는 것은 다르다
- 예산 배분 비율(`BUDGET_RATIOS`) 변경
- `base/` 를 뇌 프롬프트에서 빼는 것. 뇌가 세계관을 모른 채 검색을 정하면
  찍기가 된다는 TASK-18 REQ-RA-70의 근거를 뒤집지 않는다 (결정 7)
- 재측정. 이 변경 뒤 평가 수치가 달라지므로 별도로 다룬다

### 1.4 용어

| 용어 | 정의 |
|---|---|
| 고정 섹션 | 예산 배분 대상이 아닌 섹션. 페르소나·배경지식·감정·행동지침·내면·내적사고·응답규칙 |
| 검색 몫 | 예산에서 고정 섹션을 뺀 나머지. `search_fewshot`·`search_knowledge`·`search_memory`·`get_history`가 비율로 나눠 갖는다 |
| 계측기 | 문자열의 토큰 수를 세는 것. 실제 토크나이저 또는 보정 휴리스틱 |
| 예산 부족 | 고정 섹션만으로 예산의 전부 또는 대부분을 소진해 검색 몫이 실질적으로 없는 상태 |

## 2. 설계 결정

**결정 1 — 실제 토크나이저를 쓰되, 원격 코드는 실행하지 않는다.**
모델 공식 저장소는 `trust_remote_code`를 요구한다(P-6). 토큰 수를 세자고
남의 코드를 실행할 이유가 없다. 같은 계열의 토크나이저를 쓴다 — 실측 오차
0.6%로 충분하다(P-5).

**결정 2 — 폴백은 침묵하지 않는다.**
네트워크가 없거나 토크나이저를 구할 수 없으면 휴리스틱으로 떨어진다. 그
사실을 반드시 보고한다. **틀린 자로 재면서 그것을 모르는 것**이 이 과제의
출발점이었다. 폴백이 조용하면 같은 실패를 다시 만든다.

**결정 3 — 폴백 휴리스틱도 실측으로 보정한다.**
`한글 1.5 / 기타 0.3`은 +50% 틀린다. `response` 호출 535건에 최소제곱으로
맞춘 `한글 0.766 / 기타 0.634`는 평균절대오차 1.2%다. 폴백이 쓰이는 상황일수록
정확해야 한다.

**결정 4 — 기본값은 휴리스틱, 토크나이저는 설정으로 켠다.**
기본값을 토크나이저로 두면 테스트가 네트워크를 타고 CI가 불안정해진다.
실행 경로(CLI·API·평가 하네스)는 설정으로 토크나이저를 켜고, 테스트는
휴리스틱이나 주입된 더블을 쓴다.

**결정 5 — 예산이 모자라면 알리되 고정 섹션을 자르지 않는다.**
페르소나를 잘라 자리를 만드는 것은 정체성을 자료보다 먼저 버리는 일이다.
자산이 예산에 안 맞으면 그것은 저작의 문제이고, 런타임이 몰래 봉합할 일이
아니다 — `_report_asset_issues`(REQ-06-1)와 같은 논지다.

**결정 6 — 상한을 두는 것과 자르는 것은 다르다.**
고정 섹션에 상한을 준다. 넘으면 **보고할 뿐 자르지 않는다.** 상한이 없으면
페르소나가 길어질수록 검색이 굶는데 그 사실이 사후에만 드러난다. 상한은
"여기까지가 정상"을 선언하는 것이고, 그것을 넘었다는 보고가 저작자가 받는
신호다.

섹션별로 둔다. 합계만 보면 범인을 모른다 — `"고정 2,204"`만으로는 무엇을
줄여야 할지 알 수 없다.

값은 실측의 1.2~1.5배로 잡는다. 지금 통과하고, 눈에 띄게 커지면 걸린다.

| 섹션 | 길동 | 소민 | 상한 |
|---|---|---|---|
| 페르소나 | 670 (22.3%) | 1,009 (33.6%) | 40% |
| 배경지식 `base/` | 538 (17.9%) | 538 (17.9%) | 25% |
| 행동지침 | 275 (9.2%) | 337 (11.2%) | 15% |
| 내면 | 76 (2.5%) | 89 (3.0%) | 5% |

응답규칙·내적사고는 저작자가 통제하지 않으므로 상한 대상이 아니다. 합계
상한은 기존 `MIN_SEARCH_SHARE`가 이미 정하고 있다 — 검색 몫이 15% 미만이면
`starved`다.

**결정 7 — `base/`는 상한만 두고 구조는 유지한다.**
base는 턴당 4회 실려 비용의 25%를 쓴다(P-9 · P-10). 뇌 프롬프트에서 빼면
비용이 6%로 준다. 그러나 뇌가 세계관을 모른 채 무엇을 검색할지 정하면 찍기가
된다 — TASK-18이 측정으로 도달한 결론이고, 비용을 이유로 뒤집지 않는다.

대신 상한(25%)을 둔다. 지금 비용은 그대로지만 자산이 커지는 것은 막는다.
비용을 실제로 줄이려면 ReAct 루프가 시스템 프롬프트를 반복 전송하는 구조를
봐야 하고, 그것은 이 문서의 범위가 아니다.

## 4. 인터페이스

### 4.1 계측기

새 모듈 `src/prompts/tokens.py`:

```python
HEURISTIC_KOREAN = 0.766   # 실측 보정 (REQ-11-5)
HEURISTIC_OTHER = 0.634


class TokenCounter:
    """문자열의 토큰 수를 센다. 실제 토크나이저를 쓰고, 안 되면 휴리스틱."""

    def count(self, text: str) -> int: ...

    @property
    def method(self) -> str:
        """'tokenizer:<id>' 또는 'heuristic'. 관측용 (REQ-11-4)."""

    @property
    def fallback_reason(self) -> str:
        """폴백했다면 사유. 아니면 빈 문자열."""


def from_config(config: dict) -> TokenCounter:
    """`config.yaml`의 `prompt` 섹션으로 계측기를 만든다."""
```

토크나이저는 클래스 수준에서 캐시한다. 로드는 1.4초이고 계측은 1.5ms
미만이므로(P-7), 턴마다 다시 만들지만 않으면 지연은 문제가 되지 않는다.

### 4.2 설정

```yaml
prompt:
  # 시스템 프롬프트 예산. 생략하면 3,000
  max_tokens: 3000
  # 토큰 계측에 쓸 토크나이저. 생략하면 보정 휴리스틱을 쓴다.
  # 모델과 같은 계열이어야 한다 — mimo-v2.5는 Qwen2 계열(vocab 151,643)이다.
  tokenizer: "Qwen/Qwen2.5-7B-Instruct"
```

### 4.3 예산 보고

```python
@dataclass(frozen=True)
class BudgetReport:
    """이번 조립의 예산 내역. 로그·트레이스가 함께 쓴다."""

    max_tokens: int
    fixed_tokens: int
    search_tokens: int          # 검색 몫
    truncated: list[str]        # 잘린 섹션
    starved: bool               # 검색 몫이 하한에 못 미치는가
    method: str                 # 어느 계측기로 쟀는가
```

`PromptEngine.last_report`로 노출한다. `last_truncated`는 이 안으로 흡수한다.

검색 몫 하한은 예산의 **15%**로 둔다. 소민찌 실측 859/3,000 = 29%가
통과하고, 0%는 걸린다. 자르지 않으므로(REQ-11-7) 이 값은 경보 문턱일 뿐
동작을 바꾸지 않는다.

## 5. 검증

### 5.1 단위 테스트

| ID | 대상 | 케이스 |
|---|---|---|
| T-1 | `TokenCounter` | 토크나이저를 못 구하면 휴리스틱으로 폴백하고 예외를 던지지 않는다 |
| T-2 | `TokenCounter` | 폴백 시 `method == "heuristic"`, `fallback_reason`이 비어 있지 않다 |
| T-3 | `TokenCounter` | 주입된 토크나이저를 쓰면 `method`가 그 id를 가리킨다 |
| T-4 | `TokenCounter` | 보정 계수를 쓴다 — 같은 한글 문자열에 대해 종전 값보다 작게 센다 |
| T-5 | `TokenCounter` | 빈 문자열은 0 |
| T-6 | `from_config` | `prompt` 섹션이 없으면 휴리스틱 계측기를 만든다 |
| T-7 | `from_config` | `tokenizer`가 있으면 그것을 쓰려 시도한다 |

### 5.3 회귀 기준

- 기존 테스트 779개 통과. 계측기 기본값이 휴리스틱이므로 네트워크를 타지 않는다
- 보정 계수로 바뀌면서 기존 예산 테스트의 경계값이 달라질 수 있다. 그 경우

### 5.4 운영 관측
