## 1. 개요

### 1.1 목적

Stage 1을 **캐릭터의 뇌**로 교체한다. 뇌는 사용자 입력을 해석해 *어떤 지식과
어떤 기억이 지금 필요한지* 스스로 판단하고, 도구를 반복 호출해 근거를 모으고,
모은 것 위에서 **응답 전략**을 세운다. 최종 발화는 지금처럼 Stage 2가 맡는다.

이 문서는 구현 착수 전 단일 진실 공급원이다. 코드와 충돌하면 이 문서가 이긴다.

### 1.2 현재 상태(문제 정의)

측정된 사실이다. 추정이 아니다.

| # | 사실 | 근거 |
|---|---|---|
| P-1 | Stage 1에 LLM 호출이 없다. 전 모듈을 고정 순서로 1회씩 호출할 뿐이다 | `src/character_os.py:276` `_gather_context()` |
| P-2 | Stage 1의 산출물 `ContextBundle`이 **사용되지 않는다**. `_generate_response()`는 인자로 받고 본문에서 무시한다 | `src/character_os.py:325` |
| P-3 | 실제 컨텍스트는 `PromptEngine`이 모듈을 **다시** 호출해 만든다. 검색이 사실상 두 번 정의되어 있다 | `src/prompts/engine.py:27` |
| P-4 | 관련성 판단이 전부 고정 규칙이다. 관계 정보는 "쿼리 문자열에 이름이 들어있는가"로만 결정된다 | `src/prompts/engine.py:130` |
| P-5 | `Client.call_llm()`은 `tools`/`tool_calls`를 이미 지원하나 대화 경로에서 `tools=[]`로만 쓰인다 | `src/llm/client.py:88`, `src/character_os.py:369` |

요약: "ReAct"는 이름뿐이고, 추론·분기·반복·도구 사용이 하나도 없다.

### 1.3 범위

**포함**
- ReAct 루프(관찰 → 사고 → 도구 호출 → 관찰)의 도입
- 기존 모듈에 1:1 대응하는 도구 세트
- 응답 전략 산출물과 그것의 Stage 2 주입
- `PromptEngine`의 순수 조립기화
- 턴을 넘어 유지되는 작업기억(미해결 질문·사용자 가설)

**제외 (비목표)**
- 최종 발화 생성의 이전 — Stage 2와 Reflection은 현행 유지
- Stage 3(감정·기억·히스토리 갱신)의 에이전트화
- 외부 세계에 작용하는 도구(웹 검색, 파일 쓰기 등)
- 정적 자산(persona/knowledge/examples) 수정 — 시스템 불변식이다
- 멀티 유저, 인증

### 1.4 용어

| 용어 | 정의 |
|---|---|
| 뇌(Brain) | 본 스펙이 정의하는 ReAct 에이전트. Stage 1의 새 구현체 |
| 루프(iteration) | 뇌의 LLM 호출 1회와 그에 따른 도구 실행 0회 이상 |
| 사고 번들(ThoughtBundle) | 뇌가 Stage 2에 넘기는 산출물. 수집 컨텍스트 + 응답 전략 |
| 응답 전략 | 무엇을 알고 있는지 · 무엇을 말할지 · 어떤 태도로 갈지에 대한 뇌의 결론 |
| 작업기억(WorkingMemory) | 턴을 넘어 유지되는 미해결 질문과 사용자 가설 |
| 상한 도달 | 루프 수가 `MAX_ITERATIONS`에 닿아 강제 마감된 상태. 실패가 아니다 |

인터뷰(2026-08-18)로 확정했다. 각 결정은 되돌릴 수 있으나 되돌리면 이 문서를 먼저 고친다.

| ID | 결정 | 채택안 | 기각안과 사유 |
|---|---|---|---|
| D-1 | 뇌의 책임 범위 | 컨텍스트 수집 + 응답 전략까지. 발화는 Stage 2 | 발화까지 흡수 → 페르소나 프롬프트와 도구 추론 프롬프트가 섞여 톤이 무너지고 Reflection·평가 하네스 구조를 손대야 함 |
| D-2 | 도구 입도 | 기존 모듈 API에 1:1 대응하는 검색 도구 | 1인칭 의미 도구 → 매핑 계층 추가. 통합 검색 1개 → 소스별 전략 차별화 불가 |
| D-3 | 루프 종료 | `finish` 도구로 자발 종료 + 반복 상한 | 사전 트리아지 → 분류 호출 1회 추가. 고정 2패스 → 재귀 불가 |
| D-4 | 상한 도달 시 | 수집분으로 **정상 진행**. 트레이스·로그에 기록 | 턴 실패 → 복잡한 입력에서 사용자가 답을 못 받음 |
| D-5 | 프롬프트 조립 | `PromptEngine`은 순수 조립기. 모듈 직접 호출 제거 | 섹션 추가만 → 검색 이중 실행, 뇌의 판단이 프롬프트를 지배하지 못함 |
| D-6 | 뇌 실패 시 | **턴 실패**. 고정 규칙 폴백 없음 | 폴백 → 품질 저하가 조용히 숨는다. REQ-06 문화와 상충 |
| D-7 | 작업기억 내용 | 미해결 질문 + 사용자 가설 | 사고 요약 전체 → history와 중복, 토큰 증가 |
| D-8 | 작업기억 저장 | `state/` 아래 독립 JSON. 해소 시 제거 + 감쇠 | memory DB 합류 → 검증된 사실과 미확정 추측이 같은 검색에 섞임 |
| D-9 | 기본 상태 | 페르소나·행동지침·내면·감정·최근 대화는 프롬프트에 직접 싣고, 지식은 **목차만** 싣는다 | 지식 본문까지 → 루프마다 재전송되어 캐릭터가 커질수록 비용이 선형 증가. 최소만 → 자기가 무엇을 아는지 몰라 검색을 찍는다 |

### D-9 배경 (2026-08-18, 실사용 발견)

v1.0은 D-2("모듈 1:1 도구")를 문자 그대로 적용해 감정까지 도구로 만들었다.
그 결과 뇌는 **자기 상태를 모르는 채로** 판단을 시작했고, 실사용에서 세 가지가 드러났다.

- 매 턴 `get_emotion`을 부르느라 루프를 낭비한다 (NFR-RA-02 미달의 직접 원인)
- 무엇을 아는지 몰라 지식 검색을 찍는다 — 모른다는 것을 모르는 상태
- 최근 대화가 없어 "그 사람", "아까 그거" 같은 지시어를 해석하지 못한다

원칙을 다시 세운다. **항상 참인 것은 프롬프트에, 찾아야 아는 것은 도구에.**

## 5. 인터페이스 설계

### 5.1 새 구성요소

```
src/agent/
    brain.py            ReActBrain — 기본 상태 조립, 루프 제어, 종료 판정, 사고 번들 생성
    tools.py            ToolRegistry — 도구 정의(JSON 스키마)와 모듈 바인딩
    schemas.py          ThoughtBundle · ResponseStrategy · ToolCall 기록
src/modules/
    working_memory.py   WorkingMemoryModule — 동적 모듈. load/to_prompt/apply/save/snapshot/restore
```

`src/analysis/`가 아니라 `src/agent/`인 이유: analysis는 Stage 3의 단발 추출기이고,
뇌는 루프와 상태를 가진 제어 주체다. 같은 층에 두면 성격이 섞인다.

### 5.2 계약

```python
class ReActBrain:
    def think(self, user_input: str) -> ThoughtBundle: ...
```

```python
@dataclass(frozen=True)
class ResponseStrategy:
    situation: str = ""
    intent: str = ""
    avoid: str = ""
    tone: str = ""

    def is_empty(self) -> bool: ...     # 상한 도달 시 전략은 비어 있다

@dataclass(frozen=True)
class NewThought:
    kind: str                            # "question" | "hypothesis"
    content: str
    confidence: float = 0.0

@dataclass
class ThoughtBundle:
    strategy: ResponseStrategy
    baseline: dict[str, str]             # 도구 없이 뇌가 이미 알던 것 (감정·최근 대화)
    collected: dict[str, str]            # 도구명 → 결과 텍스트 (호출한 것만)
    iterations: int
    hit_cap: bool
    tool_calls: list[ToolCallRecord]
    resolved_ids: list[str]
    new_thoughts: list[NewThought]
```

`new_items: list[WorkingMemoryItem]` 대신 `new_thoughts: list[NewThought]`인 이유:
id와 턴 번호를 부여하는 책임은 작업기억 모듈에 있다. 뇌가 id를 지어내면
`resolved`가 참조할 대상과 어긋난다.

```python
class PromptEngine:
    def assemble_system_prompt(self, persona, bundle: ThoughtBundle) -> str: ...
    last_truncated: list[str]            # 직전 조립에서 예산에 걸려 잘린 섹션
```

### 5.3 파이프라인 변경

```
Stage 1  ReActBrain.think()  → ThoughtBundle          (LLM 1~5회, 라벨 react)
Stage 2  PromptEngine.assemble(persona, bundle) → LLM  (현행 유지, Reflection 포함)
Stage 3  emotion/memory/history + working_memory 영속   (기존 롤백 계약에 편입)
```

### 5.4 하위 호환

`PromptEngine.assemble_system_prompt()`의 시그니처가 바뀐다. 호출부는
`src/character_os.py`와 테스트뿐이며 외부 API는 영향받지 않는다.
`ContextBundle`은 제거한다 — 사용되지 않는 타입이다(P-2).

`MeteredClient`가 응답 본문이 비었다는 이유로 호출을 "프로바이더 거부"로 집계하고 있었다.

### 실측 (hong-gil-dong, 실제 LLM)

**v1.0 — 기본 상태 없음**

| 입력 | 루프 | 도구 순서 |
|---|---|---|
| "안녕" | 4 | `get_history` → `search_memory` → `get_emotion` |
| "요즘 아버지 생각이 자꾸 나는데…" | 4 | `search_memory` → `get_history` → `search_knowledge` |

**v1.2 — 기본 상태 주입 후 (D-9)**

| 입력 | 루프 | 도구 |
|---|---|---|
| "안녕" | **2** | `search_memory` |
| "요즘 아버지 생각이 자꾸 나는데…" | 3 | `search_fewshot`, `search_knowledge` |
| "그 사람이랑은 결국 화해했어?" | 4 | `get_history`, `search_knowledge`, `search_memory` |

세 가지가 확인된다.

- **적응형 깊이가 실제로 작동한다.** 입력이 복잡해질수록 루프가 2 → 3 → 4로 늘었다.
- **감정 조회 낭비가 사라졌다.** `get_emotion` 호출이 0이 되면서 단순 인사가 4루프에서
  2루프로 줄었다. 뇌 프롬프트는 3,079자로 늘었지만 루프가 줄어 상쇄된다.
- **지시어를 해석한다.** "그 사람"을 아버지로 풀어 `search_knowledge("사용자의 아버지 관계")`를
  발행했다. v1.0에서는 최근 대화를 모르니 불가능했던 판단이다.

**NFR-RA-02는 여전히 엄밀히는 미달이다** (목표 1루프, 실측 2루프). 다만 원인이
"자기 상태를 모름"에서 "기억을 한 번 확인하고 넘어감"으로 바뀌었고, 후자는 낭비라고
단정하기 어렵다. 추가 튜닝은 실사용 데이터를 더 모은 뒤 판단한다.

측정된 바 없다. 별도 과제로 남긴다 (TASK-08·09의 연장선).

## 6.8 인접 결함 (v1.3에서 함께 고침)

뇌와 별개로, 파이프라인 전역에 걸친 결함 둘이 실사용 로그에서 드러났다.
둘 다 사용자에게는 "reflection에서 멈춤"이라는 하나의 증상으로 보였다.

### 결함 1 — LLM 클라이언트에 요청 타임아웃이 없다

`openai.OpenAI()`에 `timeout`을 주지 않아 SDK 기본값(600초)이 적용되고 있었다.
실측에서 **374초 만에 성공한** `response` 호출이 3건 있다. 실패가 아니라 정상
응답이었고, 그래서 어떤 방어도 작동하지 않았다. 웹 UI는 캐릭터당 스레드 하나로
직렬 처리하므로(`src/api/worker.py`), 이 6분 동안 이후 요청이 전부 큐에서 대기한다.

- 요청 타임아웃을 도입한다 (기본 120초, `OPENAI_TIMEOUT`으로 조정)
- 타임아웃은 기존 재시도 경로에 편입한다 — 일시적 지연은 재시도로 통과한다

### 결함 2 — Reflection 출력이 폭주한다

검토기가 `PASS`를 내면서 **2,938 출력 토큰**을 쓴 사례가 있다 (7개 기준을 하나씩
논평). TASK-09가 이 문제를 프롬프트로 다뤘고 `MAX_FEEDBACK_CHARS`(200)를 두었으나,
그것은 **생성이 끝난 뒤** 자르는 장치라 지연에는 아무 효과가 없다.

- 검토·뇌 호출에 출력 상한을 건다. 프롬프트 지시만으로는 강제되지 않는다

## 7. 인수 기준

1. 사용자 입력에 따라 호출되는 도구의 종류와 순서가 달라진다 — 고정 순서가 아니다
2. 하나의 턴에서 도구 결과를 보고 추가 검색을 수행하는 사례가 트레이스로 관찰된다
3. 검색이 턴당 한 번만 실행된다(엔진의 중복 검색 제거)
4. 뇌가 실패하면 응답도 상태 변경도 없고, 사유가 로그에 남는다
5. 미해결 질문이 다음 턴 뇌의 판단에 실제로 반영된 사례가 트레이스로 관찰된다
6. 전 테스트 통과, 골든 데이터셋 점수 비회귀
