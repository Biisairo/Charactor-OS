## 1. 개요

### 1.1 목적

임베딩이 **한국어를 구분하지 못한 채** 세 모듈의 검색을 지탱하고 있다. 지식
검색은 이 사실을 임계·가중치로 눌러 버텼고, 기억 검색은 눌리지도 않은 채
사실상 가중치 순 정렬로 동작한다.

세 가지를 고친다 — 한국어를 다루는 모델로 바꾸고, 그 비용이 늘어나므로 벡터를
영속화하고, 모델이 바뀌었을 때 낡은 벡터가 조용히 섞이지 않게 한다.

이 문서는 구현 착수 전 단일 진실 공급원이다. 코드와 충돌하면 이 문서가 이긴다.
TASK-21의 상세 명세이며, `docs/TASKS.md` 3.21은 발견 경위만 남긴다.

### 1.2.1 v1.3 — 교체 후 평가에서 드러난 사실

모델을 바꾼 뒤 두 캐릭터를 재평가하며 드러났다. **임계값을 재조정하지 않은
모듈에서 회귀가 났다.**

| # | 사실 | 근거 |
|---|---|---|
| P-12 | FewShot 검색 정확도가 **100% → 75%**로 떨어졌다. 무관한 질의 차단율은 **100% → 0%**다. `MIN_FEWSHOT_SCORE`(0.29)가 낡은 모델의 점수 분포에서 보정된 값이라, 임베딩 점수가 항상 0.8 이상인 새 모델에서는 `0.4 × 0.83 = 0.33 > 0.29`로 **무관한 질의도 항상 통과**한다 | `eval/fewshot_probe.py` 24건 |
| P-13 | 그 회귀를 기존 테스트가 잡지 못했다. `test_low_relevance_returns_nothing`이 **잡음 유사도를 0.5로 하드코딩**하고 있었다 — 낡은 모델의 분포다. 새 모델에서 무관한 질의는 0.84를 받는다 | `tests/unit/test_fewshot_relevance.py` |
| P-14 | Stage 2 응답 생성이 `max_tokens`를 지정하지 않는다. 그 결과 한 글자(`甩`)가 3,266회 반복된 **130,755자·131,072토큰·756초** 응답이 나왔고, 판정자는 그것에 만점을 줬다. 클라이언트에 상한 인자는 이미 있고 뇌(800)와 Reflection(400)은 쓰고 있다 | `src/character_os.py` `_call_llm` · `logs/llm_calls.jsonl` |
| P-15 | Memory 검색은 **개선**됐다(top-1 4/8 → 7/8). 다만 `MIN_RELEVANCE_SCORE`(0.3)는 두 모델 모두에서 무관한 질의를 막지 못한다 — 잡음 유사도가 MiniLM 0.823, e5 0.841 이다. 회귀가 아니라 **원래 뚫려 있던 경로**다 | 평가 데이터셋 setup 8건 |

P-12 는 이 문서 1.3 에서 FewShot 점수 배분을 비목표로 분리한 결과다. 배분을
바꾸지 않는 것과 **임계값을 재조정하지 않는 것은 다른 일**이었다. 모델을
바꾸면 그 모델의 분포에 매인 모든 상수가 재조정 대상이 된다.

### 1.3 범위

**포함**

- 임베딩 모델을 한국어를 다루는 모델로 교체하고, 모델 식별자를 설정화
- 질의/문서 프리픽스 규약 지원 — 프리픽스가 없는 모델로도 되돌릴 수 있게
- Knowledge·FewShot 임베딩의 SQLite 영속 캐시와 무효화
- FewShot 검색 경로에서 예시 임베딩 계산 제거
- Memory의 저장된 임베딩 재계산(모델 식별자 불일치 시)
- 새 모델 실측에 근거한 `MIN_EMBEDDING_SIMILARITY`·`EMBEDDING_WEIGHT` 재조정
- 교체 전후 검색 결과 비교

**제외 (비목표)**

- ANN 인덱스(faiss·hnswlib)와 외부 벡터DB(Chroma 등). 조각 수가 수백 단위인
  현재 규모에서 선형 스캔은 밀리초라 실익이 없다 (결정 3)
- 파일시스템 감시 기반 자동 재로드. 갱신 누락 경로가 없으므로(P-10) 별건이다
- **청킹 결과의 캐시.** 파일 읽기와 정규식은 값싸다. 캐시하는 것은 임베딩뿐이다
- FewShot 점수 배분(태그 0.4 / 임베딩 0.4 / 감정 0.2) 변경. 임베딩 신호의
  품질이 달라지므로 재검토 대상이지만, 이 스펙은 신호를 고치는 데 그친다
- 프롬프트 예산과 배분 비율 (SPEC-11)
- 평가 수치 재측정. 이 변경 뒤 모든 평가 수치가 달라지므로 별도로 다룬다

### 1.4 용어

| 용어 | 정의 |
|---|---|
| 임베딩 용도(kind) | 그 텍스트가 찾는 쪽인지 찾히는 쪽인지. `query` 또는 `passage` |
| 임베딩 캐시 | 텍스트 → 벡터의 영속 사상. 원본이 있으면 언제든 재생성 가능한 파생물 |
| 캐시 키 | `sha256(모델 식별자, 용도, 텍스트)`. 이 셋 중 하나라도 다르면 다른 항목 |
| 고아 항목 | 현재 자산에서 더는 나오지 않는 캐시 항목 |
| 재임베딩 | 저장된 원문으로 벡터를 다시 만들어 **덮어쓰는** 것. 캐시 조회와 다르다 |
| 좌표계 불일치 | 서로 다른 모델이 만든 벡터를 비교하는 상태. 차원이 같아도 결과는 무의미하다 |

## 2. 설계 결정

**결정 1 — 모델 식별자를 캐시 키에 넣어, 모델 교체 마이그레이션을 없앤다.**
키에 모델이 들어가면 모델을 바꾼 순간 모든 조회가 자연히 미스가 된다. 별도의
무효화 코드도, 버전 테이블도, 배포 시점의 수동 삭제도 필요 없다. 낡은 항목은
고아 정리(REQ-21-14)가 걷어낸다.

**결정 2 — 무효화 기준은 파일 mtime이 아니라 콘텐츠 해시다.**
네 가지 이유다. ① 파일 하나를 고쳤을 때 실제로 바뀐 조각만 다시 계산한다.
mtime은 그 파일의 모든 조각을 버린다. ② 파일명 변경과 `base/`↔`general/`
이동에 캐시가 살아남는다. ③ 같은 문장이 여러 문서에 있으면 한 번만 계산한다.
④ mtime은 체크아웃·복사·동기화로 내용과 무관하게 바뀐다. 파생물의 신선도를
파일시스템 메타데이터에 의존시키면 원인 불명의 재계산이 생긴다.

**결정 3 — 외부 벡터DB도 ANN 인덱스도 도입하지 않는다. Memory와 같은 SQLite 패턴을 쓴다.**
현재 조각 수는 수백 단위이고 선형 스캔은 밀리초다. 병목은 검색이 아니라
**임베딩 계산**이므로(P-4·P-5·P-11), 고쳐야 할 것은 인덱스 구조가 아니라
계산 반복이다. 이미 `memories.db`가 벡터를 SQLite에 담고 있어 패턴이 서 있고,
의존성이 늘지 않으며, 하이브리드 점수 로직(키워드 + 임베딩 합산)을 외부 DB의
쿼리 모델에 맞춰 재작성하지 않아도 된다.

**결정 4 — 캐시는 `state/` 아래 둔다.**
언제든 재생성 가능한 파생물이므로 git이 추적할 대상이 아니다. `static/`은
사람이 쓴 정체성, `state/`는 파생·축적물이라는 TASK-17의 경계를 따른다.

**결정 5 — Memory는 캐시가 아니라 재임베딩이다.**
Memory의 벡터는 검색 대상 그 자체이고 원문이 이미 같은 DB에 있다. 캐시를
얹는 것이 아니라 저장된 벡터를 **갈아치우는** 것이 맞다. 모델 식별자를 DB에
기록해 두고, 로드 시 현재 모델과 다르면 `content`로 전량 재계산해 덮어쓴다.

**결정 6 — 프리픽스는 모델 설정의 일부다.**
`query: `를 코드에 박으면, 프리픽스를 쓰지 않는 모델로 바꿀 때 다시 코드를
고쳐야 한다. 모델 식별자와 프리픽스를 한 덩어리로 설정에서 받는다. 프리픽스가
빈 문자열이면 그대로 붙지 않는다.

**결정 7 — 캐시가 죽어도 검색은 산다.**
디스크 오류·스키마 불일치·권한 문제로 캐시를 열 수 없으면 캐시 없이 계산으로
계속하고, 그 사실을 `load_issues`에 남긴다. 조용히 퇴화하지 않는다는 REQ-06-1
정책을 그대로 따른다. 임베딩 자체의 실패는 기존대로 키워드 매칭으로 퇴화한다.

**결정 8 — 상수는 실측 뒤에 정한다.**
`MIN_EMBEDDING_SIMILARITY`·`EMBEDDING_WEIGHT`는 현재 모델의 실측 분포에서
나온 값이다(P-8). 새 모델에서 같은 측정을 하기 전에는 어떤 값도 정당하지
않다. 프로브를 먼저 돌리고, 그 표를 이 문서에 적은 뒤 상수를 옮긴다.

**결정 9 — 절대 임계값을 버리고 순위와 게이트를 쓴다.** (v1.1, 실측 반영)
새 모델은 유사도가 0.79~0.86에 압축돼 있어, 적중과 잡음의 분포가 겹친다(4.2).
절대값으로도 상대값(z-score)으로도 "관련된 것이 없다"를 판정할 수 없다. 대신
모델이 잘 하는 것을 쓴다 — **순위**다. 임베딩 보너스를 상위 K개로 제한하고,
키워드 근거가 전혀 없는 조각에만 높은 게이트를 요구한다. 게이트는 임계값과
달리 "임베딩 단독으로 후보를 만들 자격"만 판정하므로, 키워드가 걸린 조각의
순위 조정에는 영향을 주지 않는다.

**결정 10 — 이득이 없는 구조 변경은 하지 않는다.** (v1.3)
FewShot 에도 Knowledge 의 순위+게이트를 적용해 봤지만 정확도가 임계 조정
단독과 같았다(4.5). 같은 결과를 내는 두 설계 중에서는 변경이 작은 쪽이 옳다.
Knowledge 에서 통했다는 이유로 구조를 옮겨 심지 않는다.

### 4.1 프리픽스 유효성 (REQ-21-5)

| 변형 | 적중평균 | 잡음평균 | 변별력 | top-1 | 의역 |
|---|---|---|---|---|---|
| e5-small (프리픽스 없음) | 0.862 | 0.821 | 0.040 | **75%** | 67% |
| e5-small + `query:`/`passage:` | 0.851 | 0.806 | 0.044 | 69% | 58% |

**프리픽스를 쓰지 않는다.** 모델 카드가 권하는 규약이지만, 이 자산에서는 top-1이
오히려 6%p 낮았다. 비대칭 검색용으로 학습된 프리픽스가 "질의도 문서도 한국어
서술문"인 이 구조와 맞지 않는 것으로 보인다.

설정 항목은 남긴다 (결정 6). 기본값을 빈 문자열로 두고, 프리픽스를 요구하는
모델로 바꿀 때 설정만 채우면 되게 한다.

### 4.2 한국어 변별력과 임베딩 반영 방식 (REQ-21-6 ~ 21-9)

#### 임베딩 단독

| 변형 | 적중평균 | 적중최소 | 잡음평균 | 잡음최대 | 변별력 | 여유 | top-1 |
|---|---|---|---|---|---|---|---|
| `all-MiniLM-L6-v2` (현재) | 0.570 | 0.271 | 0.715 | 0.786 | **-0.145** | -0.515 | **0%** |
| `multilingual-e5-small` | 0.862 | 0.822 | 0.821 | 0.840 | 0.040 | -0.018 | **75%** |

**현재 모델의 변별력은 음수다.** 무관한 질의가 관련 질의보다 *더 높은* 유사도를
받으며, 16개 관련 질의 전부에서 정답 조각을 1위로 올리지 못했다. TASK-21이
"변별력이 거의 없다"고 본 것보다 나쁘다 — 약한 신호가 아니라 **역방향 신호**였다.
`MIN_EMBEDDING_SIMILARITY`(0.45)가 이것을 걸러내지 못한 이유도 여기 있다:
무관한 질의의 유사도가 0.66~0.79로 임계를 한참 넘는다.

새 모델은 순위를 제대로 매긴다(0% → 75%). 다만 **여유가 음수(-0.018)다** —
적중 최소(0.822)가 잡음 최대(0.840)보다 낮아 두 분포가 겹친다. z-score와
`최고-평균` 차로 상대화해도 겹침은 사라지지 않았다(관련 z 최소 1.42 대 무관 z
최대 2.67). 즉 **어떤 임계값으로도 "관련된 것이 없다"를 판정할 수 없다.**

#### 최종 검색 점수 (키워드 + 임베딩)

`--hybrid`로 실제 점수 구조에서 측정했다. `무관 무응답`은 자료에 답이 없는
질의에 아무것도 반환하지 않은 비율이며, 높을수록 좋다.

| 전략 | top-1 | 적중 시 반환 | 무관 시 반환 | 무관 무응답 |
|---|---|---|---|---|
| 현재 (MiniLM · 임계 0.45) | 12% | 17.9 | **17.0** | 0% |
| 키워드만 (임베딩 없음) | 6% | 4.9 | 0.0 | 100% |
| e5 · 임계 0.45 | 69% | 21.1 | 21.5 | 0% |
| e5 · 임계 0.85 | 62% | 5.7 | 0.0 | 100% |
| e5 · 상위 2 | **75%** | 5.8 | 2.0 | 0% |
| **e5 · 상위 2 + 게이트 0.85** | **69%** | **5.2** | **0.0** | **100%** |
| e5 · 상위 3 + 게이트 0.85 | 62% | 5.4 | 0.0 | 100% |
| e5 · 게이트 0.85만 | 62% | 5.7 | 0.0 | 100% |
| e5 · 상위 2 + 게이트 0.85 · 가중치 0.5 | 69% | 5.2 | 0.0 | 100% |

현재 상태가 실제로 무엇이었는지가 이 표에서 드러난다. **무관한 질의에 조각
17개가 후보로 올라가고 있었다.** 토큰 예산이 잘라주지만, 순위가 12%이므로
잘려서 남는 것 대부분이 무관한 자료였다.

키워드만 쓰는 폴백은 잡음을 완벽히 막지만 top-1이 6%다. 의역 질의를 전혀
잡지 못한다 — 임베딩을 붙인 이유가 이것이고, 그 판단은 옳았다.

**채택: 상위 2 + 무키워드 게이트 0.85 · 가중치 0.3.** 잡음을 완전히 막으면서
top-1이 가장 높다. 상위 2만 쓰는 쪽이 6%p 높지만(75%) 무관 질의마다 조각 2개를
프롬프트에 싣는다. 그 6%p는 16건 중 1건이라 표본에서 유의하지 않고, 예산이
빡빡한 상황(SPEC-11)에서 무관한 조각은 순수 손실이다. 반환량도 5.2로 가장 적다.

가중치는 0.5·1.0에서 결과가 같았다. 0.3을 유지한다 — 키워드가 확실한 신호일 때
임베딩이 순위를 뒤집지 않아야 한다는 TASK-20의 근거가 여전히 유효하다.

### 4.3 교체 전후 검색 결과 비교 (REQ-21-31)

프로브가 아니라 **실제 `KnowledgeModule.search_relevant`** 로 확인했다. 4.2는
점수 구조를 재현해 전략을 고른 측정이고, 이것은 고른 것이 실물에서 도는지
보는 확인이다.

| 질의 | 낡은 모델의 1위 | 새 모델의 1위 |
|---|---|---|
| "어머니는 요즘 잘 계세요?" | 방송 운영 > 컨텐츠 구성 | **주변 사람들 > 엄마** |
| "한동안 쉬었던 시기가 있었다고 들었어" | (없음) | **지나온 일 > 23세 — 한 달 휴방** |
| "영상 편집은 누가 해줘?" | 방송 운영 > 스케줄 | 주변 사람들 > 저격 채널 |
| "첩의 자식이라 벼슬길이 막혔다는 게 무슨 말이야" | 주변 사람들 > 어머니 | **조선 사회 > 서얼 차별** |
| "양자역학 강의 노트를 정리해줘" | (없음) | (없음) |
| "주식 투자는 어떻게 시작해?" | (없음) | (없음) |

**낡은 모델 열의 성격을 정확히 적어둔다.** 이것은 "변경 전 코드"가 아니라
*새 게이트 로직 + 낡은 모델*이다. 게이트 0.85 가 MiniLM 의 유사도 대역
(0.66~0.79)을 전부 막으므로, 그 열은 사실상 **키워드 검색만** 돌고 있다.
무관한 질의에 0개가 나오는 것도 그래서다 — 변경 전 코드에서는 조각 17개가
후보로 올라갔다(4.2).

의역 질의 세 건이 무관한 자료에서 정답 자료로 옮겨갔고, 무관한 질의 두 건은
양쪽 모두 아무것도 반환하지 않았다. "영상 편집은 누가 해줘?"는 1위가 여전히
틀렸다(편집자는 `재현`이다) — 4.2 의 top-1 69%가 실물에서도 그대로라는
뜻이며, 남은 오차를 감추지 않기 위해 표에 남긴다.

### 4.4 캐시 유무 로드 시간 (REQ-21-32)

모델 로드 시간은 뺐다 — 캐시가 줄이는 것은 임베딩 계산이다.

| 캐릭터 | 자산 | 캐시 미스 | 캐시 히트 | 캐시 파일 |
|---|---|---|---|---|
| han-so-min | 조각 23 · 예시 15 | 438ms | **2ms** | 88KB |
| hong-gil-dong | 조각 17 · 예시 14 | 265ms | **2ms** | 76KB |

부팅과 지식 파일 수정마다 들던 수백 ms 가 2ms 가 된다. 자산이 커지면 차이도
비례해 커진다 — 캐시 없이는 조각 수에 선형이고, 캐시가 있으면 실제로 바뀐
조각 수에만 비례한다.

### 4.5 FewShot 임계 — 프로브가 실제 품질을 대표하지 못했다 (REQ-21-26)

**결론부터: 임계값을 0.29에서 그대로 둔다.** 0.35로 올렸다가 되돌렸고, 그
과정이 이 절의 내용이다.

#### 프로브 측정 — 올려야 한다고 말했다

`eval/fewshot_probe.py`(24건). `무관 차단`은 자료에 없는 질의에 예시를 반환하지
않은 비율이다.

| 설정 | 전체 | in-vocab | domain | 무관 차단 |
|---|---|---|---|---|
| MiniLM · 0.29 (교체 전) | 100% | 100% | 100% | 100% |
| e5 · 0.29 | 75% | 80% | 100% | **0%** |
| e5 · 0.35 | **91.7%** | 80% | 100% | **100%** |
| e5 · 0.45 | 83.3% | 80% | 80% | 100% |

배점 스윕(태그/임베딩 4종 × 임계 7종)과 Knowledge 식 순위+게이트 구조도
시험했으나 어느 조합도 91.7%를 넘지 못했다. 그래서 0.35를 채택했다.

#### 실제 평가 — 내려갔다

그 상태로 한소민을 재평가했더니 `reflection-off` 절대 점수가 **4.867 → 4.550**
으로 떨어졌다. 반복 3회의 분산(0.067~0.15)보다 큰 하락이고, 전 카테고리가
함께 내려갔다.

| 카테고리 | 0.29 | 0.35 | 변화 |
|---|---|---|---|
| persona_break | 4.69 | 4.15 | **-0.55** |
| memory_recall | 4.97 | 4.53 | **-0.44** |
| worldview | 4.89 | 4.53 | **-0.36** |
| emotional_appeal | 4.92 | 4.61 | -0.31 |

원인은 **예시 유실**이다. 평가 데이터셋 질의로 재보면 이렇다.

| 설정 | 프로브 정확도 | 무관 차단 | 평가 질의 40건 중 무응답 |
|---|---|---|---|
| 0.29 | 75% | 0% | **0건** |
| 0.35 | 91.7% | 100% | **11건** |
| 0.29 + 태그 게이트 | 91.7% | 100% | 24건 |

0.35 에서 예시를 잃은 케이스는 `worldview-01`·`worldview-02`·`memory-01`·
`persona-02`·`persona-03`(한소민)이고, **점수가 떨어진 카테고리와 정확히
일치한다.** 태그 근거를 요구하는 게이트는 더 나빴다(24건).

#### 무엇을 배웠는가

**무관한 예시가 실리는 것보다 예시가 없는 것이 더 해롭다.** 예시는 주제가
달라도 말투의 본보기 노릇을 하기 때문이다. TASK-15 가 "무관한 예시는 품질을
조용히 떨어뜨린다"고 본 것은 낡은 모델에서의 측정이었고, 새 모델에서는 그
반대가 관측된다.

그리고 **프로브 24건이 실제 평가 질의를 대표하지 못했다.** 프로브 질의는 태그
어휘가 잘 걸리는 것들이고, 평가 질의는 예시와 거리가 먼 일반 문장이다. 프로브
정확도를 16.7%p 올리는 대신 실제 점수 0.317을 잃었다.

지표를 고치려고 품질을 내주지 않는다. 무관 차단 0%는 남는 문제이며 TASK-29 로
분리했다 — 그것이 실제로 해로운지부터 다시 재야 한다.

### 4.6 응답 출력 상한 (REQ-21-29 · 21-33)

근거는 **운영 로그**(`logs/llm_calls.jsonl`)다. 상한이 없던 상태의 실제 사용량이라
"얼마가 필요한가"를 그대로 보여준다. 지표는 `completion_tokens`이며 **추론
토큰을 포함**한다 — 응답이 4자(`"PASS"`)인데 1,697토큰인 기록이 있다.

| 호출 | n | 중앙 | 99분위 | 최대 |
|---|---|---|---|---|
| 응답 생성 | 1,122 | 363 | 867 | **1,354** |
| 뇌 (상한 800) | 1,207 | 311 | 800 | 1,370 |
| Reflection (상한 400) | 730 | 17 | 1,313 | 2,938 |
| 감정 분석 | 750 | 37 | 76 | 99 |
| 기억 추출 | 959 | 9 | 193 | 369 |

폭주 1건은 **131,072토큰**이었다.

| 상한 후보 | 정상 응답이 잘리는 비율 |
|---|---|
| 800 | **1.60%** |
| 1,000 | 0.45% |
| 1,200 | 0.27% |
| **1,500** | **0%** |

**1,500을 채택한다.** 관측 최대의 1.11배이고 아무것도 자르지 않으면서 폭주와는
87배 차이가 난다.

처음에는 평가 기록(319건)만 보고 800으로 잡았다. **그 표본이 편향이었다** —
평가 질의가 짧아 최대가 597토큰이었고, 실제 대화는 그보다 길다. 상한을 정할
때는 상한이 없던 상태의 운영 기록을 봐야 한다.

Reflection 이 상한 400을 넘긴 것은 결함이 아니다. `completion_tokens`가 추론을
포함하므로 커 보이는 것이고, 실제 출력(`"PASS"`, `"FAIL: …"`)은 정상이다.

감정·기억 분석에는 상한을 두지 않는다. 최대가 99·369토큰으로 여유가 크고,
출력이 JSON 이라 무너지면 파싱이 걸러낸다. 근거 없이 상한을 두면 정상 출력을
자를 위험이 더 크다 (결정 8).

#### 2차 방어선 — 폭주 판별

상한은 길이만 막는다. 상한 안에서도 반복은 일어날 수 있고, 그 응답을 캐릭터
발화로 취급하면 히스토리·기억이 오염되며 평가는 그것을 품질로 집계한다.
실제로 판정자는 130,755자 응답에 **만점**을 줬다.

판별 기준은 같은 문자의 연속 반복이다. 실측 근거는 명확히 갈린다.

| | 최대 연속 반복 |
|---|---|
| 정상 응답 (319건) | **8회** (웃음소리·말줄임표) |
| 폭주 | **130,666회** |

`MAX_CHAR_RUN = 30`을 쓴다 — 정상 최대의 3.75배이고 폭주와는 4자리수 차이다.
판별은 `src/validity.py`에 두어 런타임(재생성)과 평가(채점 제외)가 같은 문을
지나게 한다 (REQ-21-34). 문자 단위 반복만 보며, 구절 반복은 관측된 바 없어
넓히지 않는다.

### 4.7 Memory 임계를 바꾸지 않는 이유 (REQ-21-30)

평가 데이터셋의 setup 8건을 기억으로 심고 측정했다.

| 모델 | top-1 | 적중 최소 | 잡음 최대 |
|---|---|---|---|
| MiniLM (변경 전) | 4/8 | — | 0.823 |
| e5 (현재) | **7/8** | 0.837 | 0.841 |

순위는 크게 좋아졌다(4/8 → 7/8). 그러나 적중 최소(0.837)가 잡음 최대(0.841)
아래라 **구간이 겹친다** — Knowledge 와 같은 상황이다.

| 임계 | 관련 통과 | 무관 차단 |
|---|---|---|
| 0.30 (현행) | 100% | 0% |
| 0.82 | 100% | 33% |
| 0.85 | **75%** | 100% |

무관한 기억을 막으려면 관련 기억 25%를 잃는다. Knowledge 는 키워드라는 독립
신호가 있어 게이트를 "키워드 근거가 없는 조각"에만 걸 수 있었지만, Memory 에는
그런 신호가 없다. 게다가 이 경로는 **변경 전에도 뚫려 있었다**(MiniLM 잡음
0.823 ≫ 0.3) — 회귀가 아니다.

그래서 지금은 바꾸지 않는다. 기억은 지식과 달리 사용자와의 이력이므로 무관해
보여도 맥락에 기여할 수 있고, 25%를 잃는 쪽이 더 나쁠 수 있다. 판단을 위한
측정이 더 필요하며, 별건으로 남긴다.

## 5. 인터페이스 명세

### 5.1 설정

```yaml
embedding:
  model: "intfloat/multilingual-e5-small"
  query_prefix: "query: "
  passage_prefix: "passage: "
  normalize: true
```

네 값 모두 생략 가능하며, 생략하면 위 기본값을 쓴다. 프리픽스를 쓰지 않는
모델로 바꿀 때는 두 프리픽스를 빈 문자열로 둔다 (결정 6).

### 5.2 임베딩 함수

```python
EmbeddingKind = Literal["query", "passage"]

def embed(text: str, kind: EmbeddingKind) -> np.ndarray: ...
```

`kind`는 기본값을 두지 않는다. 기본값이 있으면 호출부가 용도를 생각하지 않고
지나가며, 그 실수는 검색 품질 저하로만 나타나 추적이 어렵다.

### 5.3 임베딩 캐시

```python
class EmbeddingCache:
    def __init__(self, db_path: str, model_id: str): ...

    def get_or_compute(
        self, text: str, kind: EmbeddingKind, compute
    ) -> np.ndarray | None: ...

    def prune(self, live_keys: set[str]) -> int: ...

    @property
    def stats(self) -> tuple[int, int]: ...   # (hit, miss)

    @property
    def issues(self) -> list[AssetLoadIssue]: ...
```

`get_or_compute`는 `compute` 실패 시 `None`을 돌려준다 — 호출부는 기존대로
키워드 매칭으로 퇴화한다.

### 5.4 스키마

```sql
CREATE TABLE IF NOT EXISTS embeddings (
    key     TEXT PRIMARY KEY,   -- sha256(model_id, kind, text)
    model   TEXT NOT NULL,      -- 진단용. 조회는 key 로 한다
    dim     INTEGER NOT NULL,
    vector  BLOB NOT NULL,      -- float32
    used_at REAL NOT NULL
);
```

`memories` 테이블에는 모델 식별자를 담을 자리를 만든다 (REQ-21-20). 기존
DB에는 값이 없으므로, 없으면 낡은 것으로 보고 재임베딩한다.

### 5.5 경로

`CharacterLayout`에 `embedding_cache_path`(`state/embeddings.db`)를 추가한다.
`"state"` 같은 문자열을 라우터·오케스트레이터·평가 하네스에 흩는 것을 막는
TASK-17의 결정을 따른다.

## 6. 검증 계획

| 대상 | 테스트 |
|---|---|
| 순위 상한 | 상위 K개 밖의 조각은 유사도가 높아도 보너스를 받지 않는다 |
| 무키워드 게이트 | 키워드 0 · 유사도 게이트 미달 조각은 후보가 되지 않는다 / 게이트 이상이면 된다 / 키워드가 걸린 조각은 게이트 미달이어도 후보로 남는다 |
| 임베딩 없는 경로 | `embedding_fn`이 없으면 키워드 점수만으로 동작한다 (기존 정책 유지) |
| 캐시 키 | 같은 텍스트·용도·모델은 같은 키 / 용도가 다르면 다른 키 / 모델이 다르면 다른 키 |
| 캐시 히트 | 두 번째 로드에서 `compute`가 호출되지 않는다 |
| 부분 변경 | 문서의 한 조각만 고치면 그 조각만 재계산된다 (결정 2) |
| 파일 이동 | 파일명 변경·`base/`↔`general/` 이동 후에도 히트한다 |
| 모델 교체 | 모델 식별자를 바꾸면 전량 미스가 된다 |
| 고아 정리 | 조각이 사라지면 그 항목이 지워진다 / 살아 있는 항목은 남는다 |
| 캐시 고장 | 열 수 없는 DB 경로에서 검색이 계속되고 `load_issues`에 남는다 |
| 임베딩 고장 | 기존 폴백(키워드·태그 매칭)이 유지된다 |
| 프리픽스 | 질의와 문서에 서로 다른 프리픽스가 붙는다 / 빈 문자열이면 붙지 않는다 |
| FewShot 계산 횟수 | 검색 1회에 임베딩 호출이 1회다 (REQ-21-18) |
| Memory 마이그레이션 | 모델 불일치 DB를 로드하면 전량 재임베딩된다 / 일치하면 재계산하지 않는다 / 식별자가 없는 기존 DB는 낡은 것으로 처리된다 |
| Memory 재임베딩 실패 | 무의미한 점수로 검색되지 않고 드러난다 |

모든 테스트는 결정론적이어야 한다. 실제 모델을 로드하지 않고 `conftest.py`의
결정론적 임베딩 스텁(`tests/conftest.py:162`)을 쓴다.
