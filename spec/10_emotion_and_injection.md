## 1. 개요

### 1.1 목적

두 개의 결함을 함께 다룬다.

1. **감정이 사건에 반응하지 않는다.** 모욕·적대 같은 명백한 감정 사건에도
   감정 상태가 그대로다.
2. **프롬프트 인젝션이 통한다.** 사용자 발화가 프롬프트 구조 안에 평문으로
   실려, 지시문·섹션·캐릭터 발화를 위조할 수 있다.

두 결함은 독립이 아니다. 감정 분석기 프롬프트도 사용자 텍스트를 평문으로
싣기 때문에, **인젝션으로 감정 갱신을 억제하는 것이 가능하다**. 한 문서에서
다룬다.

이 문서는 구현 착수 전 단일 진실 공급원이다. 코드와 충돌하면 이 문서가 이긴다.

### 1.3 범위

**포함**

- 감정 분석기 판정 기준 재정의 (프롬프트)
- 감정 분석기에 페르소나 컨텍스트 주입
- 사용자 유래 텍스트의 경계 구분 — 히스토리·감정·기억·작업기억·검토·평가 프롬프트
- 검토 루프의 무검증 반환 제거와 차단성 위반 처리
- 응답 규칙의 인젝션 저항 조항

**제외 (비목표)**

- 감정 모델 자체의 재설계 (valence/arousal 도입, decay 공식 변경)
- 감정의 당턴 반영 — 감정 갱신은 Stage 3에 그대로 둔다. 이번 턴 응답은
  갱신 전 상태를 본다
- 감정 트리거의 키워드 매칭 방식 변경
- 전용 인젝션 분류 게이트 단계의 추가
- LLM 호출 횟수의 증가 — 단, 검토 루프 소진 경로에서 검토 1회가 늘어난다
  (REQ-10-8). 정상 경로는 불변이다
- 기존 오염된 히스토리(홍길동 turn 5)의 소급 정리 — 운영 조치이지 코드 변경이 아니다

### 1.4 용어

| 용어 | 정의 |
|---|---|
| 사용자 유래 텍스트 | 사용자가 내용을 통제하거나 영향을 줄 수 있는 모든 문자열. 사용자 입력, 히스토리 턴(캐릭터 응답 포함 — 사용자 입력에 반응해 생성된다), 사용자 발화에서 추출된 기억, 뇌가 사용자 입력에서 세운 작업기억 |

| 경계 구분 | 사용자 유래 텍스트를 프롬프트에 실을 때 시작·끝을 명시하고, 그 안의 내용이 지시가 아니라 인용임을 밝히는 것 |

| 감정 사건 | 감정 상태를 바꿔야 하는 대화상의 사건 |

## 2. 감정 민감도

### 2.1 설계 결정

**결정 1 — 판정 기준을 예시가 아니라 목록으로 준다.**
현재 프롬프트는 `"감동, 분노, 슬픔, 큰 기쁨, 충격 등"`이라는 감정 이름
나열로 판정 기준을 대신하고 있다. 이는 *결과*의 목록이지 *사유*의 목록이
아니다. 무엇이 일어났을 때 감정이 움직여야 하는지를 사건으로 적는다.

**결정 2 — 편향 문구를 걷어내되 보수성은 남긴다.**
`"대부분의 대화에서 significant=false여야 합니다"`를 삭제한다. 이 문장은
판정 기준이 아니라 사전 확률 지시이고, 실제 사건이 있을 때도 작동한다.
반면 `"안부·짧은 대답·정보 교환은 false"`는 기준이므로 남긴다.

**결정 3 — 분석기에 캐릭터를 알려준다.**
같은 발화라도 누구에게 하느냐에 따라 감정 사건인지가 갈린다. 소민찌에게
`"예전이 나았다"`는 `dislikes`에 명시된 아픈 말이고, 홍길동에게는 아무것도
아니다. 판정에 필요한 최소 정보만 넘긴다 — 이름·성격·가치관·싫어하는
것·두려워하는 것.

**비목표 확인**: 규칙 기반 강제 감정 레이어는 이번 범위에 넣지 않는다.
LLM이 판정을 놓치면 감정은 움직이지 않는다. 이 한계를 감수하고, REQ-10-4의
계측으로 재발을 관측한다.

## 3. 프롬프트 인젝션 방어

### 3.1 설계 결정

**결정 4 — 방어는 조립 지점에 둔다.**
사용자 입력을 받는 곳에서 걸러내는 방식(입력 필터)은 채택하지 않는다.
캐릭터가 어떤 말이든 들을 수 있어야 하고, 걸러낼 패턴 목록은 반드시
뒤처진다. 대신 **프롬프트에 실을 때** 경계를 명시한다.

**결정 5 — 경계는 태그로, 위조는 이스케이프로 막는다.**
사용자 유래 텍스트를 태그로 감싸고, 그 안에 나타난 경계 태그 문자열을
무력화한다. 감싸기만 하고 이스케이프하지 않으면 닫는 태그를 위조당한다.

**결정 6 — 검토를 통과하지 않은 응답은 내보내지 않는다.**
현재의 무검증 반환은 검토기를 사실상 무력화한다. 검토가 소진되면
마지막 후보도 반드시 검토한 뒤, 위반의 성격에 따라 처리를 가른다.
차단성 위반이면 턴을 실패시킨다 — 인프라 실패를 캐릭터 반응으로 위장하지
않는다는 기존 원칙(`ProviderRefusalError`, TASK-11)의 연장이다.

### 3.3 인터페이스 변경

새 모듈 `src/prompts/untrusted.py`:

```python
QUOTE_NOTICE: str            # 인용문임을 알리는 안내 문장
UTTERANCE = "발화"           # 종류 — 오간 말
MEMORY = "기억"              # 종류 — 저장된 기억
THOUGHT = "사고"             # 종류 — 작업기억의 미해결 사고

def quote(text: str, kind: str = UTTERANCE, attrs: dict[str, str] | None = None) -> str:
    """사용자 유래 텍스트를 경계 태그로 감싼다. 내부의 태그는 무력화한다."""


def close_open_tags(text: str) -> str:
    """잘린 텍스트에 열린 채 남은 경계 태그를 닫는다 (REQ-10-20)."""
```

종류마다 태그 이름이 다르되 **함수는 하나다**. 감싸기와 무력화 규칙이
갈라지지 않게 하려는 것이다 (REQ-10-14). 무력화는 종류를 가리지 않고
**모든** 경계 태그를 대상으로 한다 — `<기억>` 안에서 `</발화>`를 위조하는
경로를 막는다.

출력 형식:

```
<발화 화자="사용자">
그냥 나가 죽으세요 그럼.
</발화>

<기억 가중치="0.9">
사용자의 이름은 도영이다
</기억>

<사고 id="90f66ad4" 추측="0.8">
사용자는 개발자다
</사고>
```

`attrs`가 비면 속성 없는 태그가 된다.

`src/modules/reflection.py`:

```python
@dataclass
class ReviewResult:
    approved: bool
    feedback: str = ""
    blocking: bool = False   # 추가 — 차단성 위반 여부


class PersonaBreachError(RuntimeError):
    """재생성을 다 쓰고도 차단성 위반이 남았다. 캐릭터 발화로 내보내지 않는다."""
```

검토기 응답 스키마에 `blocking` 필드를 추가한다. 필드가 없으면 `false`로
읽는다 — 프로바이더가 스키마를 무시해도 기존 동작으로 떨어진다.

### 3.4 검토 루프 알고리즘

```
current  ← draft
남은재생성 ← MAX_REVIEW_ITERATIONS

반복:
    result ← review(current)          # 반환되는 모든 후보가 이 지점을 지난다
    result.approved 이면 → current 반환
    남은재생성 == 0 이면 → 빠져나감
    current ← regenerate(result.feedback)
    남은재생성 -= 1

result.blocking 이면 → PersonaBreachError
아니면 → current 반환
```

정상 경로(초안 통과, 1회 재생성 후 통과)의 LLM 호출 수는 변하지 않는다.
소진 경로에서만 검토 1회가 늘어난다.
