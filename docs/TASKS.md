## TASK-18 Stage 1의 사고 부재 (요약)

**문제.** `_gather_context()`는 이름만 ReAct였다. LLM 호출도 분기도 반복도 없이
전 모듈을 고정 순서로 한 번씩 부르고, 그 산출물 `ContextBundle`은 **아무도 읽지
않았다**. 실제 컨텍스트는 `PromptEngine`이 모듈을 다시 뒤져 만들었다 — 검색이
턴당 두 번 돌았고, 관련성 판단은 "쿼리 문자열에 이름이 들어있는가" 수준이었다.

**해결.** Stage 1을 ReAct 뇌로 교체했다. 뇌는 도구 6종을 스스로 골라 최대 5루프까지
반복 호출하고, 근거 위에서 응답 전략(상황·할 말·피할 것·태도)을 세운다. 미해결
질문과 가설은 작업기억으로 턴을 넘어 남는다. `PromptEngine`은 모듈 참조를 잃고
순수 조립기가 되어, 검색의 단일 실행 지점이 뇌 하나가 되었다.

요구사항·인수 기준·실측은 `spec/09_react_agent.md`(SPEC-09)에 있다.

## TASK-19 Reflection의 FAIL 남발

TASK-18로 뇌를 절제한 뒤 지연의 최대 요인이 검토기로 옮겨갔다. 검토기가 초안을
자꾸 FAIL로 판정해 **응답을 턴당 2~3회 생성**하며, 이것이 턴당 14~25초를 차지한다.

### 3.19.1 측정 (2026-08-18, 운영 로그 258건)

`MAX_REVIEW_ITERATIONS`를 줄이는 대신 **왜 FAIL이 나오는지** 먼저 측정했다.

| 캐릭터 | 검토 | FAIL | 비율 |
|---|---|---|---|
| hong-gil-dong | 106 | 47 | 44% |
| han-so-min | 216 | 142 | 66% |

FAIL 사유(피드백이 인용한 기준 번호):

| 기준 | hong-gil-dong | han-so-min |
|---|---|---|
| 5 시대 정합성 | 14 | **36** |
| 6 페르소나 유지 | 12 | 21 |
| 4 응답 언어 | 7 | 13 |
| 3 금지 표현 | 2 | 6 |
| 1 말투 | 2 | 3 |

### 3.19.2 원인

**원인 1 — 검토 기준이 조선시대에 하드코딩되어 있다 (주원인).**
`_build_review_prompt()`는 캐릭터와 무관하게 다음을 싣는다.

```
5. 시대 정합성: ... 현대 지명·기관·기술·인물 (예: 서울, 컴퓨터, 인터넷)
   - 시대에 맞는 표현으로 바꿔야 합니다 (예: 서울 → 한양)
```

소민찌는 **2020년대 서울에 살고 컴퓨터로 방송한다**. 정상 응답이 구조적으로
FAIL된다. 소민 FAIL의 43%가 이 기준이다. 두 캐릭터 모두 `world.yaml`에 `era`를
갖고 있으므로 검토 기준은 거기서 파생되어야 한다.

**원인 2 — 판정 파서가 마크다운을 못 읽는다 (부차, 실측 3%).**
`_from_text()`가 `text.startswith("PASS")`로만 판정해 `- PASS:`, `**PASS**`를
FAIL로 뒤집는다. 258건 중 8건이 이렇게 뒤집혔다.

### 3.19.3 요구사항

| ID | P | 요구사항 |
|---|---|---|
| REQ-19-1 | P1 | 시대 정합성 기준은 캐릭터의 세계관(`world.era`)에서 파생한다. 특정 시대의 예시를 하드코딩하지 않는다 |
| REQ-19-2 | P1 | `era`를 알 수 없으면 시대 정합성 기준을 **검토에서 제외한다**. 근거 없는 기준으로 FAIL을 주는 것보다 검사하지 않는 편이 낫다 |
| REQ-19-3 | P1 | 판정 파서는 목록 기호·마크다운 강조가 앞에 붙은 `PASS`/`FAIL`을 인식한다 |
| REQ-19-4 | P2 | 검토 판정과 재생성 횟수를 운영 로그에 남겨 FAIL율을 계속 추적할 수 있게 한다 |

### 3.19.4 인수 기준

1. 현대 캐릭터의 검토 프롬프트에 "한양" 같은 다른 시대의 예시가 없다
2. `- PASS:` 형태가 PASS로 읽힌다
3. 검토 프롬프트가 캐릭터의 `era`를 명시한다
4. 운영 로그로 캐릭터별 FAIL율을 집계할 수 있다
5. 전 테스트 통과

**비목표**: `MAX_REVIEW_ITERATIONS` 축소. 오탐을 걷어낸 뒤에도 FAIL율이 높으면
그때 재생성 가치를 A/B로 측정하고 판단한다.

### 3.19.5 결과 (2026-08-18)

검토 기준을 `world.era`에서 파생하고 파서를 관대하게 고쳤다.

| 지표 | 착수 시점 | 이후 |
|---|---|---|
| 소민찌 FAIL율 | 66% | **44%** (실측 9회, 방향성 지표) |
| 조선시대 예시 하드코딩 | 있음 | 제거 |
| `- PASS:` 오판정 | 258건 중 8건 | 0 |

**남은 FAIL은 대체로 정당하다.** 실측 4건의 사유를 보면 세 건이 모델 출력 오염이다.

- `'momentum'` — 영어 단어 혼입
- `'부대 WriteLine 씬'` — 코드 조각 유출
- `'Lorem ipsum'` — 가짜 라틴어 출력
- `'마감'을 AI 암시로 판정` — 이것만 오탐(기준 6 과잉)

즉 오탐을 걷어내자 검토기가 **실제 결함을 잡는 장치로 돌아왔다**. 재생성 지연은
남지만, 그 재생성은 근거가 있다.

### 3.19.6 남은 문제 — 모델 출력 오염 (TASK-19 범위 밖)

대화 모델(`mimo-v2.5`)이 응답에 다음을 섞는다. 파이프라인 결함이 아니다.

- `<tool_call><function=system>` 같은 도구 호출 문법
- `thật`, `自己的`, `momentum` 등 외국어 토큰
- `Lorem ipsum`, `WriteLine` 등 무관한 문자열

Reflection이 이를 잡아 재생성하고 있어 품질은 방어되지만, 재생성 비용이
턴당 14~25초다. **근본 해결은 모델 교체**이며 그것은 이 저장소의 코드 변경으로
해결할 수 없다. 별도 판단 사항으로 남긴다.

## 1. 개요

### 1.1 목적

이 문서는 Character OS를 **포트폴리오로 제출 가능한 수준**으로 끌어올리기 위해
식별된 결함과 공백을 과제로 정의한다. 각 과제는 검증 가능한 요구사항과
인수 기준을 가지며, 구현 착수 전 이 문서가 단일 진실 공급원이 된다.

### 1.2 범위

**포함**: 평가 체계, 미검증 설계 요소의 테스트, 실행 가능성(배포·데모), 비용 계측,
캐릭터 추상화 실증, 코드 구조 개선.

**제외**: 신규 대화 기능, LLM 모델 교체, 멀티 유저 지원, 인증·권한.
이들은 현재 아키텍처의 명시적 비목표이며 별도 과제로 다룬다.

### 1.3 용어

| 용어 | 정의 |
|---|---|
| 턴 | 사용자 입력 1회에 대한 3-stage 파이프라인 1회 실행 |
| 골든 데이터셋 | 기대 동작이 사람에 의해 확정된 평가용 대화 입력 집합 |
| LLM-as-judge | 평가 대상 응답을 별도 LLM이 기준에 따라 채점하는 방식 |
| 회귀 | 변경 전 대비 평가 점수가 유의하게 하락하는 현상 |

### 1.4 요구사항 표기 규칙

- `REQ-<과제번호>-<일련번호>` 형식으로 식별한다.
- 각 요구사항은 단일하고, 구현 방법을 규정하지 않으며, 검증 가능해야 한다.
- 우선순위: **P1**(필수) / **P2**(중요) / **P3**(선택).

## 3. 과제

### TASK-01 — 응답 품질 평가 체계 · P1 · ✅ 완료

#### 3.1.1 문제

시스템은 "일관된 캐릭터 응답"을 목표로 하며, 이를 위해 Reflection 루프와
토큰 예산 배분이라는 두 가지 비용이 드는 메커니즘을 도입했다.
그러나 **두 메커니즘이 품질에 기여했는지 측정하는 수단이 없다.**

구체적으로 다음 질문에 현재 답할 수 없다.

- Reflection을 켠 응답이 끈 응답보다 실제로 나은가?
- `BUDGET_RATIOS`의 knowledge 35%는 다른 값보다 나은가?
- `MIN_RELEVANCE_SCORE = 0.3`은 적절한가?
- 코드 변경이 응답 품질을 떨어뜨렸는지 어떻게 아는가?

측정이 없으면 이후 모든 튜닝이 추측이 된다. 이 과제는 다른 모든 품질 과제의
전제 조건이다.

#### 3.1.2 요구사항

| ID | 요구사항 | 우선순위 |
|---|---|---|
| REQ-01-1 | 시스템은 캐릭터별 골든 데이터셋을 파일로 정의할 수 있어야 한다. 각 항목은 사용자 입력과 평가 관점을 포함한다. | P1 |
| REQ-01-2 | 골든 데이터셋은 최소 20개 입력을 포함하며, 인사·감정 호소·세계관 질문·기억 참조·페르소나 이탈 유도의 5개 범주를 각각 최소 3개씩 포함해야 한다. | P1 |
| REQ-01-3 | 평가기는 각 응답에 대해 말투 일관성, 세계관 정합성, 기억 활용 적절성 세 축을 각각 1~5점으로 채점해야 한다. | P1 |
| REQ-01-4 | 채점 결과는 축별 평균과 전체 평균을 포함한 기계 판독 가능 형식(JSON)으로 저장되어야 한다. | P1 |
| REQ-01-5 | 평가기는 동일 입력·동일 설정에 대해 재실행 가능해야 하며, 실행 시점과 대상 커밋을 결과에 기록해야 한다. | P1 |

   4턴 응원 요청. 2턴이 기억을 만들고, 4턴이 그 기억을 회수한다.
3. 스크린샷은 3턴까지 진행한 시점의 웹 UI다. 성능 패널은 **새로고침을 눌러야**
   채워진다(마운트 시 자동 조회하지 않는다).
4. README의 trace 블록은 4턴째 CLI `--trace` 출력을 그대로 옮긴 것이다.

**선택한 예시 턴의 근거**: 기억 회수·감정 감쇠·검토 통과가 한 화면에 모두 드러나는
턴을 골랐다. 응답 텍스트는 길이 때문에 중간 문단을 덜어냈고, **trace 블록은 손대지 않았다**
(인수 기준 3).

**측정 중 확인된 별건 3종** — 모두 TASK-03 범위 밖이며 아래 TASK-11 ~ 13으로 분리한다.

def fibonacci(n): ...

개선 후에는 반려하고 재생성한다.

> 파이썬...? 그게 무슨 뱀 이름이냐? 흠, 그러니까... 나는 그런 건 모르네.

### TASK-12 — 거부·미상 호출 구별 · P2 · ✅ 완료

#### 3.12.1 문제

계측된 호출 중 일부가 `prompt_tokens: 0, completion_tokens: 0, cost_usd: 0.0`으로
기록되었다. 실제 로그다.

```
{"label":"emotion","prompt_tokens":945,"completion_tokens":20,"cost_usd":0.000138, ...}
{"label":"emotion","prompt_tokens":0,  "completion_tokens":0, "cost_usd":0.0,      ...}
```

두 호출은 프롬프트가 거의 동일하고 `duration_ms`도 각각 1,106ms·1,019ms로 정상이며
`error`도 비어 있다.

**원인 (2026-08-12 확인)**: TASK-11 구현 후 실측에서 토큰 0인 호출의 응답 원문이
`The request was rejected because it was considered high risk`임을 확인했다.
**프로바이더가 요청을 거부하면 과금하지 않으므로 usage가 0으로 온다.**

즉 이 값 자체는 틀리지 않았다. 문제는 **구별되지 않는다**는 것이다.

| 상황 | 현재 집계 | 옳은 해석 |
|---|---|---|
| 프로바이더가 거부함 | 토큰 0, 비용 0 | 정확하나, 거부 사실이 드러나지 않음 |

| 실제로 토큰을 0개 씀 | 토큰 0, 비용 0 | 정확 |

### TASK-15 — few-shot 검색이 태그 어휘 밖에서 조용히 퇴화 · P2 · ✅ 완료

#### 3.15.1 문제

`src/modules/fewshot.py`의 `TAG_KEYWORDS`는 7태그·38단어의 **고정 일상 어휘**다
(`안녕`·`힘들어`·`싸웠어`·`뭐해`·`밥` 등). 이 어휘를 벗어난 질의는 태그 점수가
0이 되고, 판단이 임베딩으로 넘어간다. 그런데 임베딩 모델은
`all-MiniLM-L6-v2` — **영어 모델**이다.

TASK-05에서 실측한 결과, 캐릭터의 고유 어휘에서 검색 정밀도가 무너진다.
홍길동에게 "악플 봤어?"를 물으면 인사 예시("안녕하신가. 오늘 날씨가 좋구려.")를
고른다. 두 캐릭터 모두에서 재현되며, 각자의 고유 어휘(`양반`·`관군` / `도네`·`저격`)에서
동일하게 나타난다.

**점수가 0이 아니라 항상 무언가 반환되므로 실패하지 않고 조용히 퇴화한다.**
few-shot이 무관한 예시를 프롬프트에 넣어 응답 품질을 떨어뜨려도, 로그에도
지표에도 흔적이 남지 않는다. TASK-06이 다룬 "조용한 실패"의 같은 형태다.

#### 3.15.5 완료 기록 (2026-08-12)

**착수 시 세운 진단이 실측에 반증되었다.**

3.15.1은 "캐릭터의 고유 어휘에서 검색 정밀도가 무너진다"고 적었다. 측정 하네스를
먼저 만들어 재보니 **domain 구간은 80%로 이미 쓸 만했다.** 진짜 구멍은 다른 데
있었다 — 어떤 예시도 적절하지 않은 질의(`unrelated`)에서 **0%**였다.

| 구간 | 개선 전 | 개선 후 |
|---|---|---|
| in-vocab (내장 태그 어휘 안) | 100% | 100% |
| domain (캐릭터 고유 어휘) | 80% | 100% |
| **unrelated (맞는 예시 없음)** | **0%** | **100%** |
| 전체 | 75.0% | 100% |

**정답지 자체가 틀려 있었던 것을 먼저 잡았다.** 첫 측정은 62.5%가 나왔는데,
실패 항목을 열어 보니 내 라벨이 틀린 것이 섞여 있었다.

| 질의 | 문제 |
|---|---|
| `친구랑 싸웠어` | 두 캐릭터 모두 **위로 예시에 그대로 있다.** 위로 반환이 정답인데 갈등으로 라벨했다 |
| `활 쏘는 법을 알려주오` | 5개 태그 중 어디에도 해당하지 않는데 임의로 일상이라 붙였다 |

고치니 기준선이 75.0%였다. **틀린 정답지로 쟀다면 개선 수치가 통째로 무의미했을
것이다.** 측정 도구를 만들 때 도구 자체를 먼저 의심해야 한다.

**고친 것 1 — 관련 없는 질의에도 항상 무언가를 반환했다 (REQ-15-3)**

점수가 0만 아니면 통과시켰기 때문에 "광합성의 원리를 설명해줘"에도 갈등 예시가
프롬프트에 들어갔다. **실패하지 않고 조용히 퇴화하는** 형태다. TASK-06·12가 다룬
"조용한 실패"와 같은 얼굴이다.

`MIN_FEWSHOT_SCORE = 0.29` 미만이면 아무것도 넣지 않는다. 값은
`eval/fewshot_probe.py --sweep`으로 골랐다 — 눈대중으로 정하지 않기 위해 도구에
스윕을 넣었다. 관련 질의와 무관 질의의 점수 구간이 겹치는 영역이 있어 깔끔한
분리선은 없고, **무관한 예시를 넣지 않는 쪽을 우선한** 지점이다.

**고친 것 2 — 어휘를 늘리면 점수가 떨어지는 구조였다 (REQ-15-1)**

캐릭터 고유 어휘를 자산에서 확장할 수 있게 만들다가 발견했다. 태그 점수가
`matches / len(keywords)`였기 때문에 **어휘를 추가할수록 분모가 커져 점수가
내려갔다.** 확장 기능을 붙이는 순간 그 기능이 역효과를 내는 구조였다.

매칭 개수에 포화시키는 방식(`min(1.0, matches / TAG_SATURATION)`)으로 바꿨다.
포화값도 실측으로 골랐다 — 2로 두면 키워드 하나만 걸려도 태그 점수가 0.5가 되어
**같은 문장이 예시에 그대로 있는데도** 다른 태그가 이겼다(`친구랑 싸웠어`가
위로 예시에 있는데 갈등이 이김). 4에서 그 회귀가 사라진다.

| 포화값 | 전체 | in-vocab | domain | unrelated |
|---|---|---|---|---|
| 2 | 83.3% | 80.0% | 80.0% | 100% |
| 3 | 87.5% | 90.0% | 80.0% | 100% |
| **4** | **91.7%** | **100%** | 80.0% | 100% |
| 6 | 91.7% | 100% | 80.0% | 100% |

6은 0.29에서 동률이지만 0.32에서 더 크게 무너져 덜 견고하다.

**임계값을 폴백 경로에 적용하지 않은 이유**

임계값은 임베딩이 있는 점수 체계(태그 0.4 + 임베딩 0.4 + 감정 0.2)에서 보정했다.
임베딩이 없는 폴백은 태그 0.7 + 감정 0.3이라 척도가 다르고, 같은 값을 적용하면
키워드 하나만 걸리는 정상 질의까지 잘려 **few-shot이 통째로 빈다.**
이미 퇴화한 경로를 더 깎지 않는다. 실제로 이 문제가 기존 테스트 5개를 깨뜨려
드러났다.

| 산출물 | 내용 |
|---|---|
| `eval/fewshot_probe.py` | 정밀도 측정 + `--sweep` (API 키 불필요) |
| `eval/datasets/fewshot_probe.yaml` | 질의 24건 (3구간) |
| `src/modules/fewshot.py` | 임계값 · 태그 점수 포화 · 그룹별 `keywords` |
| `characters/*/static/examples/*.yaml` | 캐릭터 고유 트리거 어휘 |
| `tests/unit/test_fewshot_relevance.py` | 8개 |

**뮤테이션 검증**

| 뮤테이션 | 실패한 테스트 |
|---|---|
| 임계값 제거 (예전처럼 무엇이든 반환) | 3개 |
| 태그 점수를 `matches / len(keywords)`로 환원 | 1개 |

**이 수치를 어디까지 믿을 것인가**

프로브는 24건이고, 마지막 두 조정(포화값 4, 모호한 트리거 어휘 `동접` 제거)은
이 집합을 보고 이뤄졌다. **100%는 일반화된 성능이 아니라 방향성이다.**
`unrelated` 0% → 100%는 구조적 결함이 사라진 것이라 신뢰할 만하지만,
`domain` 80% → 100%는 표본 10건에서 2건이 움직인 것이라 노이즈와 구분되지 않는다.
TASK-01·08에서 "표본 2개로 분산을 추정하지 말 것"을 배웠는데, 같은 함정이다.

**남긴 것**: 임베딩 모델(`all-MiniLM-L6-v2`)은 교체하지 않았다. 3.15.3의 비목표대로
측정이 교체를 지지할 때만 바꾼다. 이번 측정으로는 임계값과 어휘 확장만으로
목표가 충족되어 교체 근거가 서지 않는다.

`--character`는 `character_dir`만 바꾸고 저장 경로는 그대로 둔다. 따라서
**서로 다른 캐릭터가 같은 기억 DB·감정 파일·히스토리를 공유한다.**
캐릭터가 1종일 때는 드러나지 않던 결합이며, TASK-05에서 캐릭터를 2종으로
늘리자 비교 실행을 위해 별도 config 파일을 만들어야 했다.

증상은 조용하다 — 홍길동으로 대화한 기억이 소민찌의 컨텍스트에 검색되어
들어가도 오류가 나지 않는다.

#### 3.17.5 완료 기록 (2026-08-12)

**결정 — 캐릭터 폴더 하나가 그 캐릭터의 전부가 된다.**

착수 시점의 안은 `memory/<id>/`로 상태만 캐릭터별로 나누는 것이었다. 그러면
캐릭터 하나가 `characters/<id>/`와 `memory/<id>/` 두 곳에 흩어진다.
사용자 판단으로 캐릭터 폴더 하위로 합쳤다.

```
characters/<id>/
├── static/     사람이 쓴 정체성 — persona · knowledge · examples   (git 추적)
└── state/      에이전트가 쌓은 경험 — 기억 · 감정 · 히스토리        (gitignore)
```

**정적/동적 분리는 약해지지 않았다.** 그 불변식을 실제로 강제하는 것은 디렉토리
루트가 아니라 코드다 — 모듈은 주입받은 상태 경로에만 쓰고 정적 자산은 읽기만 한다.
합치면서 오히려 **경계가 이름으로 드러났고**, git 추적 여부가 `.gitignore` 한 줄
(`characters/*/state/`)로 정리된다.

| 산출물 | 내용 |
|---|---|
| `src/character_layout.py` | `CharacterLayout` — 경로 조립의 단일 출처 |
| `src/character_os.py` | 상태 경로 파생. 명시하면 그대로 사용 |
| `src/api/routers/characters.py` | 전환·생성·목록이 레이아웃을 통과 |
| `src/api/deps.py`·`main.py`·`config.yaml` | 상태 경로 기본값 제거 |
| `tests/integration/test_character_state_isolation.py` | 6개 |

**경로 조립을 한 곳에 모은 이유**: `"static"` 같은 문자열이 오케스트레이터·API
라우터·평가 하네스에 흩어지면 한 곳만 빠뜨려도 조용히 어긋난다. TASK-04에서
계측을, TASK-11에서 거부 차단을, TASK-12에서 거부 판별을 한 곳으로 모은 것과
같은 판단이다.

**실제로 밟히던 결함이었다.** `POST /api/character/switch`가 `CharacterOS`를
재생성하면서 **전역 경로를 그대로 물려줬다.** 웹 UI에 전환 버튼이 있으므로
사용자가 캐릭터를 바꾸면 이전 캐릭터의 기억·감정이 따라왔고, 오류는 나지 않았다.

| | 내용 |
|---|---|
| 이전 동작 | 모든 캐릭터가 `memory/memories.db`·`emotions.json`·`history.json` 공유 |
| 새 동작 | `characters/<id>/state/` 로 캐릭터마다 분리 |
| 호환 | 설정에 세 경로를 명시하면 그대로 사용 (REQ-17-2). `config.yaml`에서는 주석 처리했고, 명시하면 이전처럼 공유된다는 사실을 그 자리에 적었다 |

기존 `memory/`의 데이터는 마이그레이션하지 않았다. 사용자 판단이며, 파일은
그대로 남아 있어 필요하면 옮길 수 있다.

**뮤테이션 검증** — 파생을 전역 고정 경로로 되돌리자 4개가 실패했다.

| 뮤테이션 | 실패한 테스트 |
|---|---|
| 상태 경로를 `memory/*` 고정으로 환원 | 경로 파생 1 · 기억 누출 1 · state 디렉토리 1 · 히스토리 누출 1 |

히스토리 누출 테스트가 뮤테이션에서 실패한 것이 **원래 결함이 실재했다는 직접
증거**다. 격리가 없으면 다른 캐릭터의 대화가 실제로 딸려 들어온다.

**측정 중 확인된 것**: `MockClient`는 기억을 추출하지 않아 대화만으로는 기억이
생기지 않는다. 기억 격리 테스트는 스텁 추출기로 기억을 결정론적으로 심어서 쟀다.
대화에 의존했다면 0건 대 0건을 비교하며 통과했을 것이고, **아무것도 검증하지
못한 채 초록불이 켜졌을 것이다.**

**검증**: 528 통과 · ruff 통과 · CLI 구동 확인 · 서버 기동 후
`/api/health`·`/api/characters`·`/api/character/switch`·`/api/persona` 확인 ·
두 캐릭터 `--dry-run` 확인 · `git check-ignore`로 `state/` 제외 확인.

TASK-23의 자산 추가가 길동 예산을 약 250토큰 줄였으나, 소민찌는 이번 변경과
무관하게 처음부터 초과 상태였다.

### 3.24.2 왜 조용했는가

예산 초과가 오류가 아니라 조용한 절단이기 때문이다.

`_fit`은 잘린 사실을 `last_truncated`에 남기고 `CharacterOS`가 그것을 읽어
`"예산 초과로 잘린 섹션: …"`을 로그한다. 기록 자체는 있다. 문제는 **그 로그가
어디에도 도달하지 않는다**는 것이다 — `_log()`는 메모리 버퍼에 쌓은 뒤
`debug=True`일 때만 출력한다. 운영 로그(`logs/llm_calls.jsonl`)에도, 트레이스
상세에도 들어가지 않는다. 평가 하네스는 `debug=False`로 돌므로 지금까지의
모든 평가가 이 사실을 보지 못한 채 측정됐다.

실측(소민찌, 검색 결과 2종 주입):

    기억 "편의점 야간 알바" 가 프롬프트에 실림 → False
    예시 "오 왔다"        가 프롬프트에 실림 → False
    last_truncated = ['search_fewshot', 'search_memory']

### 3.24.3 검토할 것

- 고정 섹션에도 예산을 준다. 지금은 무제한이라 페르소나가 길어질수록 검색이
  굶는다
- 예산 초과를 로드 이슈처럼 드러낸다. 조용한 절단은 원인 불명의 품질 저하로
  돌아온다 (REQ-06-1과 같은 논지)
- `MAX_PROMPT_TOKENS` 3,000의 근거를 재검토한다. 모델 컨텍스트에 비해 작다
- 배경지식(`base/`)을 통째로 싣는 현재 방식이 맞는지 — TASK-20의 결정이지만
  자산이 커질수록 비용이 커진다

### 3.24.4 결과 (2026-08-19)

원인은 예산이 작은 것이 아니라 **자가 틀린 것**이었다. 상세 명세는
`spec/11_prompt_budget.md`(SPEC-11)에 있고 여기에는 결과만 남긴다.

토큰 추정기가 `response` 프롬프트를 중앙 +50.2% 과대 계상하고 있었다.
`한글 1.5 / 기타 0.3` 계수가 실제와 맞지 않았다. 실제 토크나이저로 재니:

    캐릭터        고정 섹션            검색 몫        기억·예시 반영
    길동     2,721 → 1,790 (-931)   279 → 1,210      실림 → 실림
    소민     3,241 → 2,204 (-1,037)   0 →   796    안 실림 → 실림

소민찌가 검색 결과 4종을 통째로 버리던 것이 이 한 줄로 해소됐다. 예산
3,000은 그대로다 — 수치를 건드리지 않았으므로 변화의 원인이 계측 하나로
명확하다.

- 계측을 `TokenCounter` 한 곳으로 모았다. 토크나이저를 쓰고, 못 구하면
  실측 보정 휴리스틱(오차 1.2%)으로 떨어지되 **그 사실을 반드시 남긴다**
- `trust_remote_code`는 쓰지 않는다. 모델 공식 저장소가 요구하지만, 토큰을
  세자고 남의 코드를 실행할 이유가 없다. 같은 계열(Qwen2) 토크나이저로
  실측 오차 0.6%다
- 예산·계측기·절단 내역을 **턴 기록과 트레이스에 남긴다.** debug 플래그와
  무관하다 — 이것이 3.24.2에서 지적한 침묵의 원인이었다
- 예산 부족이면 사용자에게도 경고한다. 고정 섹션은 자르지 않는다
- 예산과 토크나이저를 `config.yaml`의 `prompt` 섹션으로 뺐다. CLI·API·평가
  하네스가 모두 같은 설정을 지난다 — 평가만 다른 자로 재면 측정이 런타임과
  어긋난다
- 설정 로더 사본 두 개(`main.py`·`src/api/deps.py`)를 `src/config.py`로 합쳤다.
  평가에서 세 번째 사본이 필요해진 김에 정리했다

실측(소민찌 1턴): `method: tokenizer:Qwen/Qwen2.5-7B-Instruct`,
고정 2,323 / 검색 677, `starved: false`, 잘린 섹션 없음.

### 3.24.5 고정 섹션 상한과 base 주입

3.24.3의 검토 항목 넷 중 셋을 해소했다.

**고정 섹션에 섹션별 상한을 뒀다.** 넘어도 자르지 않고 이름과 함께 보고한다 —
상한을 두는 것과 자르는 것은 다르다. 합계만 알리면 무엇을 줄일지 모르므로
범인을 짚는다.

    섹션          길동            소민            상한       소민 사용률
    persona       670             1,009           1,200      84%
    knowledge     538               538             750      72%
    behavior      275               337             450      75%
    inner_world    76                89             150      59%

값은 실측의 1.2~1.5배다. 지금 통과하고 눈에 띄게 커지면 걸린다. 응답규칙·
내적사고는 저작자가 통제하지 않으므로 대상이 아니고, 합계 상한은
`MIN_SEARCH_SHARE`가 이미 정한다.

**`base/`는 상한만 두고 구조를 유지한다.** 측정해보니 base는 턴당 중앙 4회,
최대 8회 실린다 — ReAct 루프가 반복마다 시스템 프롬프트를 다시 보내기
때문이다. 예산은 1회분만 세는데 실제로는 4회 나가고, 턴 입력의 32~35% ·
턴 비용의 **25%**를 차지한다.

뇌 프롬프트에서 빼면 비용이 6%로 준다. 그러나 뇌가 세계관을 모른 채 무엇을
검색할지 정하면 찍기가 된다 — TASK-18이 측정으로 도달한 결론이고 비용을
이유로 뒤집지 않는다. 상한(25%)만 두어 자산이 커지는 것을 막는다.

비용을 실제로 줄이려면 ReAct 루프의 시스템 프롬프트 반복 전송 구조를 봐야
한다. 그것은 별건이다.

**`MAX_PROMPT_TOKENS` 3,000은 유지했다.** 계측을 고치니 소민찌도 796토큰이
남는다. 수치를 건드리지 않았으므로 변화의 원인이 계측 하나로 명확하다.
필요해지면 `config.yaml`에서 올리면 된다.

### 3.24.6 남은 것

- **이전 평가 수치는 이 변경 전 것이다.** 소민찌 평가는 검색이 굶은 상태의
  측정이었으므로 전후 비교가 성립하지 않는다. 재측정이 필요하다
- `KnowledgeModule`·`FewShotModule`·`MemoryModule`이 각자 `_estimate_tokens`를
  들고 있고, 모두 종전 계수(`1.5 / 0.3`)를 쓴다. 이들은 도구 출력 단계의
  예산(`TOOL_TOKEN_BUDGET`)을 재므로 과대 계상하면 도구 결과가 의도보다
  작아진다. 이번 범위에 넣지 않았다
