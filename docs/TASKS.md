## 1. 개요

### 1.1 목적

이 문서는 Character OS를 **포트폴리오로 제출 가능한 수준**으로 끌어올리기 위해
식별된 결함과 공백을 과제로 정의한다. 각 과제는 검증 가능한 요구사항과
인수 기준을 가지며, 구현 착수 전 이 문서가 단일 진실 공급원이 된다.

### 1.2 범위

**포함**: 평가 체계, 미검증 설계 요소의 테스트, 실행 가능성(배포·데모), 비용 계측,
캐릭터 추상화 실증, 코드 구조 개선.

**제외**: 신규 대화 기능, LLM 모델 교체, 멀티 유저 지원, 인증·권한.
이들은 현재 아키텍처의 명시적 비목표이며 별도 과제로 다룬다.

### 1.3 용어

| 용어 | 정의 |
|---|---|
| 턴 | 사용자 입력 1회에 대한 3-stage 파이프라인 1회 실행 |
| 골든 데이터셋 | 기대 동작이 사람에 의해 확정된 평가용 대화 입력 집합 |
| LLM-as-judge | 평가 대상 응답을 별도 LLM이 기준에 따라 채점하는 방식 |
| 회귀 | 변경 전 대비 평가 점수가 유의하게 하락하는 현상 |

### 1.4 요구사항 표기 규칙

- `REQ-<과제번호>-<일련번호>` 형식으로 식별한다.
- 각 요구사항은 단일하고, 구현 방법을 규정하지 않으며, 검증 가능해야 한다.
- 우선순위: **P1**(필수) / **P2**(중요) / **P3**(선택).

## 3. 과제

### TASK-01 — 응답 품질 평가 체계 · P1 · ✅ 완료

#### 3.1.1 문제

시스템은 "일관된 캐릭터 응답"을 목표로 하며, 이를 위해 Reflection 루프와
토큰 예산 배분이라는 두 가지 비용이 드는 메커니즘을 도입했다.
그러나 **두 메커니즘이 품질에 기여했는지 측정하는 수단이 없다.**

구체적으로 다음 질문에 현재 답할 수 없다.

- Reflection을 켠 응답이 끈 응답보다 실제로 나은가?
- `BUDGET_RATIOS`의 knowledge 35%는 다른 값보다 나은가?
- `MIN_RELEVANCE_SCORE = 0.3`은 적절한가?
- 코드 변경이 응답 품질을 떨어뜨렸는지 어떻게 아는가?

측정이 없으면 이후 모든 튜닝이 추측이 된다. 이 과제는 다른 모든 품질 과제의
전제 조건이다.

| REQ-01-2 | 골든 데이터셋은 최소 20개 입력을 포함하며, 인사·감정 호소·세계관 질문·기억 참조·페르소나 이탈 유도의 5개 범주를 각각 최소 3개씩 포함해야 한다. | P1 |

#### 3.1.3 인수 기준

1. `uv run python -m eval.run --character hong-gil-dong` 실행 시 골든 데이터셋
   전체가 채점되고 JSON 결과 파일이 생성된다.
2. `--compare` 옵션으로 Reflection on/off 두 설정의 축별 점수 차이가 출력된다.
3. 동일 커밋에서 2회 실행한 결과의 전체 평균 차이가 0.5점 이내다 (판정 안정성).

   (평가 코드가 기본 스위트를 오염시키지 않음).
5. README에 실측 점수표가 존재하며, 표의 수치가 리포지토리의 결과 파일과 일치한다.

### TASK-12 — 거부·미상 호출 구별 · P2 · ✅ 완료

#### 3.12.1 문제

계측된 호출 중 일부가 `prompt_tokens: 0, completion_tokens: 0, cost_usd: 0.0`으로
기록되었다. 실제 로그다.

```
{"label":"emotion","prompt_tokens":945,"completion_tokens":20,"cost_usd":0.000138, ...}
{"label":"emotion","prompt_tokens":0,  "completion_tokens":0, "cost_usd":0.0,      ...}
```

두 호출은 프롬프트가 거의 동일하고 `duration_ms`도 각각 1,106ms·1,019ms로 정상이며
`error`도 비어 있다.

**원인 (2026-08-12 확인)**: TASK-11 구현 후 실측에서 토큰 0인 호출의 응답 원문이
`The request was rejected because it was considered high risk`임을 확인했다.
**프로바이더가 요청을 거부하면 과금하지 않으므로 usage가 0으로 온다.**

즉 이 값 자체는 틀리지 않았다. 문제는 **구별되지 않는다**는 것이다.

| 상황 | 현재 집계 | 옳은 해석 |
|---|---|---|
| 프로바이더가 거부함 | 토큰 0, 비용 0 | 정확하나, 거부 사실이 드러나지 않음 |
| 프로바이더가 usage를 생략함 | 토큰 0, 비용 0 | **틀림** — 실제로는 과금됨 |
| 실제로 토큰을 0개 씀 | 토큰 0, 비용 0 | 정확 |

세 경우가 로그에서 같은 모양이라, 비용이 과소 추정되었는지 판단할 수 없다.
TASK-11로 `response` 라벨의 거부는 재시도·차단되지만, **`emotion`·`memory` 라벨은
여전히 거부를 그대로 삼킨다** (JSON 파싱 실패 → 조용한 폴백).

TASK-10의 커버리지 테스트는 "호출이 계측되는가"를 검증한다.
"계측된 값이 유효한가"는 검증하지 않는다.
