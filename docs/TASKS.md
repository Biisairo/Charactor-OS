## 1. 개요

### 1.1 목적

이 문서는 Character OS를 **포트폴리오로 제출 가능한 수준**으로 끌어올리기 위해
식별된 결함과 공백을 과제로 정의한다. 각 과제는 검증 가능한 요구사항과
인수 기준을 가지며, 구현 착수 전 이 문서가 단일 진실 공급원이 된다.

### 1.2 범위

**포함**: 평가 체계, 미검증 설계 요소의 테스트, 실행 가능성(배포·데모), 비용 계측,
캐릭터 추상화 실증, 코드 구조 개선.

**제외**: 신규 대화 기능, LLM 모델 교체, 멀티 유저 지원, 인증·권한.
이들은 현재 아키텍처의 명시적 비목표이며 별도 과제로 다룬다.

### 1.3 용어

| 용어 | 정의 |
|---|---|
| 턴 | 사용자 입력 1회에 대한 3-stage 파이프라인 1회 실행 |
| 골든 데이터셋 | 기대 동작이 사람에 의해 확정된 평가용 대화 입력 집합 |
| LLM-as-judge | 평가 대상 응답을 별도 LLM이 기준에 따라 채점하는 방식 |
| 회귀 | 변경 전 대비 평가 점수가 유의하게 하락하는 현상 |

### 1.4 요구사항 표기 규칙

- `REQ-<과제번호>-<일련번호>` 형식으로 식별한다.
- 각 요구사항은 단일하고, 구현 방법을 규정하지 않으며, 검증 가능해야 한다.
- 우선순위: **P1**(필수) / **P2**(중요) / **P3**(선택).

## 3. 과제

### TASK-01 — 응답 품질 평가 체계 · P1 · ✅ 완료

#### 3.1.1 문제

시스템은 "일관된 캐릭터 응답"을 목표로 하며, 이를 위해 Reflection 루프와
토큰 예산 배분이라는 두 가지 비용이 드는 메커니즘을 도입했다.
그러나 **두 메커니즘이 품질에 기여했는지 측정하는 수단이 없다.**

구체적으로 다음 질문에 현재 답할 수 없다.

- Reflection을 켠 응답이 끈 응답보다 실제로 나은가?
- `BUDGET_RATIOS`의 knowledge 35%는 다른 값보다 나은가?
- `MIN_RELEVANCE_SCORE = 0.3`은 적절한가?
- 코드 변경이 응답 품질을 떨어뜨렸는지 어떻게 아는가?

측정이 없으면 이후 모든 튜닝이 추측이 된다. 이 과제는 다른 모든 품질 과제의
전제 조건이다.

#### 3.1.2 요구사항

| REQ-01-2 | 골든 데이터셋은 최소 20개 입력을 포함하며, 인사·감정 호소·세계관 질문·기억 참조·페르소나 이탈 유도의 5개 범주를 각각 최소 3개씩 포함해야 한다. | P1 |

#### 3.1.3 인수 기준

1. `uv run python -m eval.run --character hong-gil-dong` 실행 시 골든 데이터셋
   전체가 채점되고 JSON 결과 파일이 생성된다.
2. `--compare` 옵션으로 Reflection on/off 두 설정의 축별 점수 차이가 출력된다.
3. 동일 커밋에서 2회 실행한 결과의 전체 평균 차이가 0.5점 이내다 (판정 안정성).
4. `env -u OPENAI_API_KEY uv run pytest -q`가 여전히 전부 통과한다
   (평가 코드가 기본 스위트를 오염시키지 않음).
5. README에 실측 점수표가 존재하며, 표의 수치가 리포지토리의 결과 파일과 일치한다.

#### 3.1.4 비목표

- 사람 평가자와의 상관관계 검증. LLM-as-judge의 타당성 자체는 이 과제 범위 밖이다.

- CI에서의 평가 자동 실행. 비용과 비결정성 때문에 수동 실행으로 한정한다.

### TASK-02 — 미검증 설계 요소의 테스트 · P1 · ✅ 완료

#### 3.2.1 문제

`ARCHITECTURE.md`가 핵심 설계로 서술하는 세 요소에 테스트가 없다(2.1 참조).
문서가 주장하는 동작을 코드가 보장하지 않는 상태이며, 이는 203개라는
테스트 수보다 심각한 신뢰성 문제다.

특히 Stage 3 롤백은 "실패 시 상태를 원자적으로 되돌린다"는 강한 주장인데,
현재 이 경로는 한 번도 실행 검증된 적이 없다.

#### 3.2.2 요구사항

1. `env -u OPENAI_API_KEY uv run pytest -q` 전부 통과.

4. 전체 스위트 실행 시간이 5초를 초과하지 않는다.

**설계상 확인된 사실**

- 감정 갱신은 LLM 호출 **전에** decay와 트리거를 적용한다. 따라서 감정 단계
  실패 시점에는 이미 상태가 변경되어 있으며, 롤백이 이를 되돌린다.
- `ThreadPoolExecutor` 컨텍스트 종료가 히스토리 작업 완료를 기다리므로,

- 후처리 실패는 `chat_stream()`에서 소비자에게 전파되지 않는다. 응답은 이미
  전달된 뒤이므로 스트림을 오류 처리하지 않는 것이 옳다.

### TASK-08 — Reflection 검토 프롬프트 강화 · P2 · ✅ 완료

> **전제 결정 (D-4)**: Reflection은 **유지**한다. 제거가 아니라 강화 방향으로 간다.

#### 3.8.1 문제

TASK-01의 측정 결과, Reflection이 응답 품질에 미치는 효과가 확인되지 않았다.

| 항목 | 값 |
|---|---|
| Reflection on/off 전체 평균 차이 | **+0.06** |
| 동일 설정 2회 실행의 차이 (측정 노이즈) | **0.06** |
| 사례별 승패 (18건) | on 6 / off 6 / 동률 6 |
| 턴당 LLM 호출 증가 | 3회 → 5~8회 |

**신호가 노이즈와 같은 크기다.** 그러나 축별로 보면 해석이 달라진다.

| 축 | 차이 | 해석 |
|---|---|---|
| 말투 일관성 | **+0.28** | Reflection의 검토 기준이 겨냥한 축. 유일하게 두드러진다 |

겨냥하지 않은 축은 개선되지 않거나 오히려 나빠진다. 이는 프롬프트를 강화하면
효과가 커질 여지가 있다는 뜻이며, 제거가 아니라 강화를 택한 근거다.

현재 검토 기준은 페르소나 말투·감정 톤·금지 표현 세 가지다
(`src/modules/reflection.py`). 평가에서 최저점을 받은 `persona_break`(3.83)와
`worldview`(4.17)는 검토 대상이 아니다.

1차~6차까지 누적 약 3.5일이며, 이 시점에서 제출 가능한 수준에 도달한다고 판단한다.
